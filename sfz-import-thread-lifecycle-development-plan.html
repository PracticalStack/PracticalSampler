Critical finding 02 · Implementation roadmap

Give every SFZ import an owner, cancellation path, and shutdown barrier

Replace detached, callback-driven threads with one processor-owned, bounded worker. Each editor or standalone shell receives an RAII client handle, observes immutable generation-tagged results on the message thread, and cannot be destroyed until its active request has reached a terminal state.

  • Scope: SFZ analyze, review, and commit handoff
  • Estimate: 14–20 engineering days
  • Delivery: 6 gated phases
  • Primary risk: cooperative cancellation depth

Target outcome

Ownership

No anonymous work

A processor-owned service holds one joinable worker. UI clients are explicit, non-copyable lifetime objects; no import thread is detached.

Control

Bounded and cancelable

At most one request is running. Cancellation is observed inside parse, normalization, report, and projection loops, not only between stages.

Shutdown

Nothing survives unload

Client destruction cancels and waits for its generation; processor destruction requests stop, wakes the worker, and joins it before dependent state disappears.

Current failure and evidence

Confirmed defect

Editor::reviewSfzImportFile() and MainComponent::reviewSfzImportFile() each create a temporary std::thread and call detach(). Their destructors stop timers and save settings, but do not cancel or wait for import work. A Component::SafePointer only prevents dereferencing a deleted component after MessageManager::callAsync(); it does not own the worker or keep the plug-in module loaded.

Direct code locations

  • app/src/plugin/PluginEditor.cpp:980–1035
  • app/src/standalone/MainComponent.cpp:1065–1120
  • Editor::~Editor():541–545
  • MainComponent::~MainComponent():519–525
  • app/src/shared/SfzImportWorkflow.cpp:63–87

Secondary race exposed by the same design

The worker projects against a copied base project, but the completion later applies that projection to the current AuthoringSession without checking project ID or document revision. Opening, closing, restoring, or editing a project while review is running can make the result stale even when the UI component still exists.

Scope and boundaries

In scope

  • SFZ review request ownership, scheduling, progress, cancellation, and shutdown.
  • Cooperative cancellation seams through parser, normalizer, report, and projection.
  • Plugin and standalone parity through one shared service contract.
  • Project identity/revision validation before the review can commit.
  • Progress and cancel UI, lifecycle metrics, stress tests, and unload tests.

Non-goals

  • Do not change SFZ conversion semantics or opcode support.
  • Do not move project mutation off the message thread.
  • Do not run more than one worker to improve throughput.
  • Do not use a blocking modal progress loop.
  • Do not require C++20 std::jthread; the project is currently C++17.

Proposed ownership architecture

1 · Shell clientAn RAII client belongs to one editor or standalone shell and has a unique owner ID.
2 · SubmitCapture SFZ path, project ID, base revision, and immutable base-project copy.
3 · Owned workerA processor-owned service accepts one bounded request on one joinable C++17 thread.
4 · CheckpointsParser and projector poll generation/stop state at bounded intervals and exit with a typed disposition.
5 · PublishThe worker atomically publishes an immutable snapshot. It never queues a lambda that captures plug-in code.
6 · CommitThe shell timer consumes the matching result on the message thread and revalidates project identity/revision.

Why the processor owns the service

A plug-in editor can close and reopen while its processor remains alive. The client handle can cancel and wait for editor-owned work without destroying the reusable worker. The processor destructor is the final module-lifetime barrier and performs the actual thread join. In the standalone shell, MainComponent owns that same processor, so the identical barrier applies.

Proposed lifecycle contract

enum class SfzImportStage {
    idle, queued, analyzing, projecting, reviewReady,
    canceled, failed, consumed
};

struct SfzImportRequestIdentity {
    std::uint64_t ownerId;
    std::uint64_t generation;
    std::string projectId;
    std::size_t baseRevision;
};

struct SfzImportReviewSnapshot {
    SfzImportRequestIdentity identity;
    SfzImportStage stage;
    float progress01;
    std::string status;
    std::shared_ptr<const SfzImportReviewPreparationResult> result;
};

class SfzImportReviewService {
public:
    Client openClient();              // RAII owner for one shell
    SnapshotPtr getSnapshot() const;  // immutable, atomic publication
    void shutdown();                  // idempotent stop + join
};

class SfzImportReviewService::Client {
public:
    SubmitResult submit(Request);     // rejects while this client is busy
    bool cancel(std::string reason);
    bool waitForTerminal(std::chrono::milliseconds timeout);
    ~Client();                        // cancel + terminal barrier
};

Names are illustrative. The implementation should keep the service free of direct component pointers and UI callbacks. The existing shell timers already provide a message-thread observation point.

Threading and state invariants

InvariantRequired behaviorEnforcement
One worker, one active review No request queue can grow without bound. A second click is disabled/rejected while the client is busy. Single optional request slot plus an explicit busy submit result.
Generation wins Only the current owner/generation may update progress, display a review, or commit. Check the identity before every publication and again on the message thread.
Cancellation is cooperative A canceled import stops during large files/includes and does not wait for a whole pipeline stage. Cancellation probe at file, line/section, opcode, source, and zone boundaries.
Mutation stays serialized Worker code performs read/transform work only. It never mutates AuthoringSession. applySfzImportProjection() remains a message-thread action.
Results are immutable Readers never race a worker-owned result and late publications cannot overwrite a newer request. Atomic publication of shared_ptr<const Snapshot>.
Project context must match A result prepared for another project or revision cannot be committed silently. Compare project ID and document revision before opening review and before Apply.
Shutdown is a barrier No worker executes SFZ or JUCE code after processor teardown begins. Idempotent stop, condition-variable wake, terminal publication, and join in Processor::~Processor().

Critical path

SFZL-102 → SFZL-201/202/205 → SFZL-301–305 → SFZL-401–405 → SFZL-601/602/604. UI polish can proceed after the immutable snapshot contract is stable, but shell cutover must wait for cancellation checkpoints.

Risks and mitigations

RiskConsequenceMitigation
Cancellation is checked too coarsely. Editor/host shutdown can still block for an unacceptable interval. Deterministic pause hooks and checkpoints inside the deepest file/section/zone loops; record maximum cancellation latency.
Worker join happens too late in processor destruction. Worker reads already-destroyed engine/application state. Explicit early shutdown() in destructor body plus member-order review and a destruction-stage test hook.
A progress callback recreates the queued-code lifetime hazard. Message queue executes plug-in code after unload. Use immutable snapshot polling through existing timers; do not post worker lambdas.
Base project changes while review is open. Stale zones/sources are applied to the wrong document revision. Identity check at presentation and a second check immediately before commit.
Cancellation changes deterministic SFZ output. Existing supported imports regress. Keep default overload behavior unchanged and run fixture/corpus/determinism comparisons on every phase.
A blocking destructor wait freezes the host. Slow or hung unload. Make cancellation bounded, measure barrier latency, log timeout diagnostics in debug, and never abandon or detach the thread.

Definition of done

The issue is corrected only when all conditions hold

  • No SFZ path calls std::thread::detach().
  • One named processor-owned worker is the sole review executor.
  • Each shell owns an RAII client with a terminal destruction barrier.
  • Processor destruction performs an idempotent stop-and-join.
  • Pending and in-flight work are both bounded to one.
  • Cancellation is observed inside every expensive pipeline stage.
  • Worker results are immutable and generation-tagged.
  • No worker posts a component-capturing message-thread lambda.
  • Only the message thread mutates AuthoringSession.
  • Project ID and revision are checked twice before commit.
  • User-visible progress and cancellation work in both shells.
  • Repeated close/unload stress leaves zero live jobs.
  • All existing SFZ corpus and determinism tests remain green.
  • Plugin and standalone build/behavior parity is verified.
