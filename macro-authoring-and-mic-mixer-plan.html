Macro Authoring And Group Mixer Workflow Plan

This plan turns the current partial macro infrastructure into a complete end-user workflow for group-based instrument controls. The target outcome is simple for creators and safe for the runtime: authors can create macros inside Authoring, bind them to group-scoped gain inserts, publish the current draft, and let players control exposed layer, mic, or noise balances from the Performance surface without republishing for every mix move.

Outcome And Target Workflow

Creator outcome

A creator can author mic layers, instrument layers, pedal noise, or other controllable sources as groups, add group-scoped gain inserts, create named macros, and mark chosen macros as exposed in the Performance surface.

Player outcome

A player sees a compact mixer-style control surface in Perform and can rebalance published group levels without changing the draft or forcing a republish.

Engine outcome

The runtime still activates one immutable published payload at a block boundary, but the active published macro table carries stable exposed-control bindings into the callback and preset/state recall path.

1. Create groups - Import and assign zone layers into explicit groups such as close, room, felt, or pedal-noise.
2. Add group gain inserts - In Routing/DSP, choose group scope, ensure a routing bus exists for that group, and create a curated drs.gain insert for the bus.
3. Create macros - In the Macros drawer, create one macro per user-facing group control, choose a name, range, default value, and target binding.
4. Mark macros exposed - Explicitly opt selected macros into the Performance mixer surface so authored helper macros do not automatically clutter player UI.
5. Publish - Publish the current draft. The runtime compiles the immutable payload and stable published macro binding table.
6. Perform - The player adjusts exposed mixer controls live. Preset recall persists values; topology changes still require authoring plus Publish.

Frozen Architecture Decisions

1. Controllable sources remain groups

Mic positions, instrument layers, and ambient sources continue to be modeled as authored groups. That preserves the existing zone membership, group gain/pan, audition anchor, routing-bus ownership, and future per-group DSP path.

2. Player mixer controls remain macros

Player-facing controls are still published macros, not mutable group objects. This keeps runtime control changes in the current preset/host/activation model.

3. Exposure is explicit

Not every authored macro should appear in Perform. Exposure metadata is creator-owned and should be stable across reorder, rename, publish, and recall.

4. Host topology stays bounded

The fixed-slot macro publish model stays intact. Exposed mixer controls consume published slots just like other macros, and capacity checks must fail loudly before activation.

Recommended authored pattern: one group per controllable source, one group-scoped gain insert per exposed mixer lane, one exposed macro per user-adjustable group gain. Group pan remains optional and can follow later if stereo placement becomes part of the first shipping mixer.

Sprint 1 - Macro CRUD Foundation

Workstream: engine model + authoring session Goal: make macros first-class authored objects

Development tasks

  • M1.1 Add authoring-session API for createMacro, duplicateMacro, and deleteMacro alongside the existing update and move methods.
  • M1.2 Define stable macro ID generation rules that survive rename and reorder, and reject collisions deterministically.
  • M1.3 Add validation for empty names, invalid ranges, duplicate IDs, and invalid structured DSP target identities during authoring edits, not only at publish time.
  • M1.4 Add explicit authoring selection state for the selected macro so create/delete operations have predictable focus ownership.
  • M1.5 Decide whether exposure metadata lives on the macro definition or on the first target, and add the field to the runtime project model.
  • M1.6 Extend project load/save and schema validation to preserve the new exposure field and reject malformed values loudly.

Exit criteria

  • New macros can be created, saved, reloaded, and restored by stable ID.
  • Delete and duplicate are undoable and keep selection sane.
  • Malformed macros fail in the authoring session with actionable messages instead of silently producing bad publish input.

Sprint 2 - Authoring Workflow

Workstream: authoring UI Goal: let creators create macros without touching JSON

Development tasks

  • M2.1 Add Create Macro, Duplicate, and Delete actions to the Macros drawer with clear component IDs and keyboard reachability.
  • M2.2 Add an empty-state panel that explains what macros are for and offers one-click creation when a project has none.
  • M2.3 When creating a macro, seed sensible defaults: generated stable ID, visible default name, range 0..1, default value 0.5, and no target until the creator assigns one.
  • M2.4 Show exposure state directly in the macro list so creators can see which macros will appear in Perform.
  • M2.5 Separate assignment editing from macro existence so a brand-new macro can exist before a target is chosen.
  • M2.6 Add inline validation and disabled-state messaging for publish-blocking macro issues.

Exit criteria

  • A creator can create, rename, range-edit, expose, duplicate, and delete a macro entirely from the Authoring UI.
  • The UI handles zero macros and multiple macros cleanly.
  • The authoring UI characterization suite covers the new controls and empty-state path.

Sprint 3 - Group/Layer Control Authoring Path

Workstream: authoring UX + DSP routing Goal: make the intended group-gain-to-macro path discoverable without a special-purpose wizard

Development tasks

  • M3.1 Improve the handoff between Groups, Routing, and Macros so a creator can stay oriented while turning a selected group's gain insert into a macro target, without adding a dedicated "Create mic control" wizard.
  • M3.2 Add creator-facing copy for a general "group control" or "mixer lane" concept, without introducing a new engine object unless needed later.
  • M3.3 Improve the DSP assignment selector so group-scoped gain parameters are easy to recognize and not buried among unrelated targets.
  • M3.4 Add recommended naming suggestions derived from the selected group name so the same path works for mic positions, layered timbres, and noise sources.
  • M3.5 Preserve context from selected group to selected routing bus to selected gain parameter so assignment feels direct, while still allowing advanced manual edits.
  • M3.6 Add summary labels in Groups and Routing that show which macros currently control the active group bus.

Exit criteria

  • A creator can start from a selected group and end with a named, exposed, target-bound gain macro using the standard authoring surfaces.
  • The authoring UI no longer assumes creators understand the difference between routing, DSP target identity, and performance exposure.
  • At least one focused test covers the complete group-control authoring path.

Sprint 6 - Hardening And Release Gate

Workstream: regression coverage + docs Goal: promote the workflow from plausible to shippable

Development tasks

  • M6.2 Add capacity tests for exposed macros near and beyond the published-slot maximum.

Risks And Non-goals

Primary risks

  • We could over-generalize the macro UI and delay the actual group-control workflow.
  • Exposure metadata could drift from fixed-slot publish behavior if it is treated as purely cosmetic.
  • Group-scoped insert assumptions could break if routing-bus ownership rules are not enforced tightly.
  • The current published-macro regression may hide deeper articulation-selection or bootstrap assumptions.

Explicit non-goals for this plan

  • Arbitrary modulation graph authoring.
  • Unlimited dynamic host-parameter creation beyond the fixed published-slot model.
  • A full DAW-style mixer with sends, meters, or aux automation.
  • Changing the core "explicit Publish" performance boundary.
Do not ship a half path: exposing macro creation without exposure semantics or a clear Perform outcome would increase complexity without solving the user problem. The real feature is not "macro CRUD." The real feature is "authors can build group-based controls that players can use."
