Restore must validate and apply project-owned performance state in the context of the restored authored project, remain atomic, and always leave the user a recoverable path after failure.

Confirmed diagnosis

Why Piano Lite is silent after hosted recall

Root cause: Processor::applyValidatedProjectRestore() loads the Phase 1 reference instrument and validates the saved preset against it. Piano Lite saves articulation default; the reference instrument accepts sustain. The restore is rejected as CheckpointInvalid before the authored project reaches active playback.

1. REAPER restores statedrs.hostState contains the Piano Lite binding and selected articulation default.
2. Project resolvesThe manifest path, project identity, digest, and project checkpoint validate successfully.
3. Wrong contextThe saved preset is checked against loadPhase1ReferenceInstrument(), not Piano Lite.
4. Generic rejectionThe contextual articulation mismatch is collapsed into CheckpointInvalid.
5. No activationThe hosted performance state remains unavailable, so MIDI can arrive without playable audio.

Core renderer is healthy

Direct load and publish produced peak 0.0482, finite samples, no dropped events, and sub-millisecond render callbacks.

Hosted restore fails

The same captured state reported Failed / CheckpointInvalid and rendered a zero peak.

Single-field proof

Changing only selectedArticulationId from default to sustain made restore Active and produced peak 0.0254.

Important: removing only the validation at PluginProcessor.cpp is insufficient. EngineFacade::restorePresetStateJson() independently validates against the same reference manifest and sets reference-instrument state. The hosted restore path needs one project-aware validation and application contract used end to end.

Target outcome

Correct behavior and scope

Restore the authored context

Project-owned articulation and performance selections are validated against the restored project's projected runtime instrument.

Preserve preset compatibility

Reference-instrument preset identity, load profile, host macro values, and legacy drs.presetState behavior remain strict and backward compatible.

Fail safely and recoverably

An invalid project state cannot activate mismatched content, but a later valid manual load and publish can recover without recreating the plug-in instance.

In scope

  • Saved and dirty authored-project host recall.
  • Project-aware articulation validation and application.
  • Typed restore failure details and UI presentation.
  • Audio-silence gate cleanup and manual recovery.
  • Processor, VST3 wrapper, and REAPER regression tests.

Non-goals

  • No change to sample playback, crossfade DSP, or voice allocation.
  • No new compiled-instrument format or schema dependency.
  • No weakening of project ID, manifest digest, or publish-identity checks.
  • No file I/O, allocation, or validation work on the audio thread.

Recommended API shape: introduce a host-restore-specific context/result rather than adding permissive flags to validateRuntimePresetState(). The context should carry the reference instrument, restored authored runtime instrument, project ID, and a preserve-draft-playback policy. The result should identify the exact failed stage and issues.

Proposed engine seam

EngineFacade::restoreHostSessionPresetState(preset, context)

  • Does not call the reference-only restorePresetStateJson().
  • Does not reset the restored draft project to reference-instrument mode.
  • Applies the authored articulation only after contextual validation succeeds.
  • Returns structured stage, finding, and issue data.

Authored runtime projection

Build the validation instrument from the already validated checkpoint using buildInstrumentManifestForProject() and the resolved manifest path. This is a deterministic model projection; sample decoding remains in the existing preparation worker.

1

Regression Contract and Design Freeze

1-2 days - no behavior change

Capture the exact defect first and define which instrument owns each restored field. Avoid a narrow one-line bypass that silently weakens preset validation.

  • HSR-101 Add a minimal authored-project fixture whose only articulation is default, while the reference instrument continues to use sustain. Keep sample payload tiny.
  • HSR-102 Extend HostProjectRecallTests.cpp to capture a valid drs.hostState, restore it into a fresh processor, and assert the current CheckpointInvalid failure before the fix.
  • HSR-103 Add an audio assertion: after successful recall, MIDI note-on must produce finite, nonzero output; a status-only Active assertion is insufficient.
  • HSR-104 Add a characterization test showing that changing only the articulation to a reference-known ID makes the old path pass. Record this as diagnostic evidence, not intended behavior.
  • HSR-105 Inventory every reference-only preset validation/application call used during project recall, including PluginProcessor::applyValidatedProjectRestore() and EngineFacade::restorePresetStateJson().
  • HSR-106 Write a short ADR or update the host-state ADR to assign ownership of schema identity, load profile, macros, articulation selection, project checkpoint, and published identity.
  • HSR-107 Decide compatibility policy for drs.hostState v1: retain the schema and reinterpret the context-dependent articulation correctly unless a schema migration is proven necessary.

Primary files: tests/src/HostProjectRecallTests.cpp, host-state fixtures, docs/host-state-recall-adr.md, engine_adapter/include/drs/engine/HostSessionState.h.

Exit criteria

The regression fails for the confirmed contextual articulation mismatch; the approved contract says exactly which model validates and applies every restored field.

2

Project-Aware Validation and Application

2-3 days - core correction

Replace the two reference-only restore decisions with one explicit hosted-project restore context, while preserving the strict behavior of ordinary reference preset loading.

  • HSR-201 Introduce typed HostSessionPresetRestoreContext and HostSessionPresetRestoreResult structures in the engine adapter. Include restored project ID, authored runtime instrument, preserve-draft flag, failed stage, finding, and issues.
  • HSR-202 Implement a pure contextual validation helper that keeps preset schema/target/load-profile rules strict while resolving selectedArticulationId against the authored runtime instrument.
  • HSR-203 Define macro validation explicitly: published host macro slots remain normalized; authored macro values use authored ranges; missing or duplicate IDs produce targeted issues.
  • HSR-204 Add EngineFacade::restoreHostSessionPresetState(). Apply validated values without setting referenceInstrumentActive or reinitializing the draft project as the Phase 1 reference instrument.
  • HSR-205 In Processor::applyValidatedProjectRestore(), project checkpoint.project into a RuntimeInstrumentModel using the resolved manifest path, then call the new context-aware facade API.
  • HSR-206 Remove the direct call to loadPhase1ReferenceInstrument() for authored-articulation validation. Keep reference loading only where reference-owned preset fields genuinely require it.
  • HSR-207 Preserve atomicity: do not assign authoringSession, file binding, macro bindings, expected published identity, or playback activation until all contextual validation stages succeed.
  • HSR-208 Verify that publish-generation restoration and exact authored/macro/prepared digest checks remain unchanged after the contextual state is applied.
  • HSR-209 Add unit coverage for default, multiple custom articulations, default-articulation selection, unknown articulation, custom macros, and legacy sustain.

Primary files: app/src/plugin/PluginProcessor.cpp, app/src/shared/ProjectStorage.cpp, engine_adapter/include/drs/engine/EngineFacade.h, engine_adapter/src/EngineFacade.cpp, engine_adapter/src/RuntimePresetState.cpp.

Exit criteria

The Piano Lite-style fixture restores as Active and renders finite, nonzero audio. Existing strict reference-preset tests and legacy preset-only recall remain green.

Failure Recovery and Actionable Diagnostics

2 days - lifecycle hardening

A terminal recall failure must not leave ambiguous state or prevent the user from recovering by loading and publishing a valid project in the same plug-in instance.

  • HSR-301 Replace the boolean result from applyValidatedProjectRestore() with a structured outcome identifying checkpoint, binding, preset, articulation, draft reopen, publish scheduling, or identity failure.
  • HSR-302 Add an appropriate restore finding such as presetStateInvalid or articulationMismatch; stop reporting every application failure as CheckpointInvalid.
  • HSR-303 Include the rejected articulation ID, restored project ID, and available/default articulation IDs in off-audio diagnostics and the recovery banner.
  • HSR-304 Define terminal audio policy: never activate mismatched content; clear the pending restore gate after terminal handling; close stale playback once; leave the instance ready for a valid manual publish.
  • HSR-305 Ensure replaceAuthoringProject() and an accepted manual publish supersede any older failed restore generation and reset failure/gate state safely.
  • HSR-306 Add a same-instance recovery regression: invalid recalled articulation, confirmed failure, manual valid project load, publish, block-boundary activation, and audible MIDI.
  • HSR-307 Add concurrency coverage for a failed generation superseded by a valid restore, editor close during preparation, and processor shutdown with pending contextual validation.
  • HSR-308 Confirm no project parsing, instrument projection, string formatting, logging, sample loading, or allocation occurs in processBlock().

Primary files: app/src/plugin/PluginProcessor.h/.cpp, engine_adapter/include/drs/engine/ProjectRestoreCoordinator.h, engine_adapter/src/ProjectRestoreCoordinator.cpp, app/src/shared/HostStateRecoveryBanner.cpp.

Every failure is specific and terminal, current valid state remains atomic, and the same plug-in instance can recover through manual load/publish without removal from the DAW.

Risks and decisions

Guardrails for implementation

Do not make preset validation globally permissive

Skipping articulation validation or allowing arbitrary target identities would hide corrupt state and weaken standalone/reference preset guarantees. Use an explicit hosted-project context.

Do not apply state twice

The processor and facade must not independently validate and mutate overlapping state. One structured engine result should drive the processor transaction.

Preserve audio-thread boundaries

Runtime instrument projection and validation belong on the message/background side. Only the prepared activation token crosses to the audio block boundary.

Prefer schema v1 compatibility

The existing state already carries the needed articulation ID and project binding. Avoid a schema bump unless the ownership split cannot be represented unambiguously.

Stop-ship condition: do not release a fix that makes the processor-level test pass while the compiled VST3 or REAPER scenario remains silent. The defect exists specifically at the hosted lifecycle boundary.

Completion gate

Definition of done

  • Piano Lite's default articulation restores without renaming content.
  • The authored project, articulation, macro state, revision, and published identity round-trip exactly.
  • Processor and compiled VST3 tests produce finite, nonzero audio after recall.
  • REAPER editor-open and editor-closed scenarios both pass.
  • Unknown articulations fail with a specific finding and useful IDs.
  • A failed recall can be recovered by manual load/publish in the same instance.
  • Legacy preset-only sessions remain compatible and playable.
  • Manifest identity and digest safety checks are unchanged.
  • No sample loading, file I/O, projection, logging, or allocation occurs on the audio thread.
  • Full host-state, publish, realtime safety, articulation, macro, and shell parity suites pass in Debug and Release.
  • REAPER evidence records state schema, active identity, track peak, RMS, nonzero samples, and non-finite count.
  • ADR, recall guide, progress log, and validation evidence describe the final ownership model.
Recommended first implementation move: land Sprint 1's failing fixture and ownership ADR together. The production correction should not begin until the team agrees that articulation selection is project-owned during authored-project recall, while legacy reference-preset validation remains strict.
