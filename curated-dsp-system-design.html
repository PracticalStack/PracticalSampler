Architecture proposal · design only

Curated DSP should become a compiled, hierarchical insert graph.

Extend the existing FX-slot and routing-bus seam into a real-time-safe graph with exactly three attachment scopes: zone, group, and instrument. Keep authoring flexible, compile it into a bounded render plan off the audio thread, and keep each Preview or Performance activation generation’s mutable effect state isolated.

Short answer

Keep the existing project-owned FX slots and buses, but give them strict insert semantics and compile them into a fixed hierarchy: voices feed an optional zone chain, zones feed an optional group chain, groups feed one instrument chain, and the instrument feeds the host output. Do not put delay or reverb inside every sampler voice, do not build an unrestricted routing graph yet, and do not host arbitrary third-party plug-ins.

Why this fits: the repository already captures FX slots, routing buses, group membership, immutable snapshots, prepared playback, activation generations, and two isolated playback contexts. The missing piece is a compiled DSP graph between voice mixing and final output.

The signal model

The authored graph is deliberately more constrained than a DAW mixer. One owner may have zero or one serial insert chain. The compiler may collapse owners with no active effects, so the callback only pays for processing nodes that exist.

Sampler voices Sample playback, pitch, velocity, envelope, loop, and current route gain/pan.
→
Zone insert All simultaneous voices for one zone are summed, then processed once.
→
Group insert All member-zone results are summed, then processed once.
→
Instrument insert All groups are summed, processed, and written to the lane output.
Zone

Sound-design detail

Use for sample-specific correction or character: trim, filter/EQ, saturation, special delay, or room treatment for a single mapped zone.

Group

Layer cohesion

Use for a drum family, mic layer, articulation, or layered timbre. Shared processing happens after member zones have been combined.

Instrument

Global polish

Use for the complete instrument’s tone and space. This is the only master chain and is always last inside its playback lane.

Ordering rule: zone → group → instrument. A creator can reorder slots inside one chain, but cannot reorder the three scopes or create feedback. That makes routing deterministic, validation cheap, and scratch allocation bounded.

Recommended authoring contract

Evolve the current fields instead of adding direct reverb, delay, or distortion properties to zones and groups. The project should describe effect instances and their chain ownership; a code-owned curated catalog defines what each type means.

FX slot — one effect instance

FieldPurpose
idStable identity used by undo, macros, host recall, and chain order.
displayNameCreator-facing label; never used as runtime identity.
effectTypeCatalog key such as drs.gain, drs.saturator, drs.stereoDelay, or drs.algorithmicReverb.
effectVersionFreezes algorithm/default interpretation for reproducible recall.
bypassedClick-free runtime bypass state.
parametersOrdered stable parameter IDs and natural-unit values. Unknown values are preserved but never executed.

Routing bus — one owner’s serial chain

FieldPurpose
idStable chain identity.
displayNameCreator-facing chain label.
inputSourceIdCanonical owner reference: zones/<id>, groups/<id>, or master.
fxSlotIdsExact serial order. The same slot may belong to only one bus.
bypassedOptional chain-level A/B without mutating each slot.

Invariants that remove ambiguity

  • At most one bus may claim a particular source owner.
  • A bus may source only a zone, a group, or master; it may not source another bus in the first release.
  • Every referenced slot exists, and every executable slot is owned by exactly one bus.
  • Slot IDs and bus IDs are unique across the project.
  • A zone source resolves to exactly one authored zone, and a group source resolves to exactly one authored group.
  • There is at most one master bus.
  • Unknown effect types or unsupported versions load as preserved, bypassed objects with a visible finding.
  • Parameters are validated against the catalog; missing parameters receive versioned defaults, and out-of-range values are rejected or explicitly clamped during migration.
  • group.routingBusId becomes a compatibility field, not a second source of truth. New projects derive ownership from the bus source.

The curated catalog is a product contract

“Curated” should mean a small code-owned registry with stable IDs, parameter definitions, scope support, cost metadata, state version, and one approved implementation per effect. Projects store instances and values; they do not store executable graphs, class names, or arbitrary plug-in state blobs.

Wave Effect Core controls Why / constraint
1 Gain / trim Gain, polarity, mute First vertical slice and identity-path proof. It exercises every scope without tail or transport complexity.
1 Saturator / drive Drive, character, tone, mix, output Proves nonlinear ordering and parameter smoothing. Start without oversampling to keep latency zero.
1 Stereo delay Time or sync division, feedback, ping-pong, tone, width, mix Proves transport input, bounded delay memory, tails, and stereo state.
1 Algorithmic reverb Pre-delay, size, decay, damping, width, mix Prefer algorithmic reverb first. Convolution adds asset ownership, loading, and possible latency.
2 Filter / compact EQ Cutoff/frequency, resonance/Q, gain, mode Useful everywhere, but define a focused product surface instead of a fully general unlimited-band editor.
2 Chorus / ensemble Rate, depth, voices, width, mix Reuses modulation and delay infrastructure after the stereo delay path is stable.
Implementation boundary: the public engine contract should be product-owned and independent of any DSP library. An effect implementation may use a vetted JUCE DSP primitive internally, but HISE should not become the owner of the graph while HISE integration remains disabled and the product’s sampler core already owns deterministic rendering.

Compile authored DSP into the current activation pipeline

1 · Authoring project Editable slots, values, and scope-owned buses live in the undoable project document.
2 · Immutable snapshot Capture full slot parameters, versions, source ownership, chain order, and structured findings.
3 · Preparation Resolve catalog types, validate cost, prepare coefficients/assets, and compile a flat processing plan.
4 · Render generation Allocate mutable effect state and scratch off audio, then stage it beside the render model.
5 · Audio callback Exchange one prepared token at a block boundary and execute only bounded, precomputed nodes.

Immutable compiled plan

  • Flat effect-node array in exact processing order
  • Zone route → processing-node index
  • Zone node → group node → master node destination indices
  • Parameter-slot bindings and smoothing metadata
  • Required scratch channels, delay memory, tail class, and cost estimate
  • Stable DSP graph digest included in prepared and publish conformance

Mutable per-generation state

  • Filter histories, delay lines, reverb state, smoothers, and bypass ramps
  • Preallocated block scratch and bus accumulators
  • Tail-active flags and bounded silence detection
  • No shared mutable state between Preview and Performance
  • No allocation, locks, file I/O, catalog lookup, or object destruction in the callback

Stable target identity

Macros should resolve a structured target made from:

  • FX slot ID
  • Parameter ID
  • Optional mapping curve
  • Minimum and maximum destination values

Do not use display names or fragile free-form path parsing as the long-term binding contract.

Host automation policy

Keep the plug-in’s fixed host parameter topology. The curated effects may expose many creator controls inside the editor, but only authored macros become DAW-visible automation parameters. During publish, macro targets compile into bounded callback slots that address DSP parameters by stable slot/parameter identity. This preserves host recall when effect chains are reordered and avoids illegal dynamic host parameter creation.

Tempo-aware effects: extend the render request with a small primitive transport view—tempo, time signature, play state, and sample position. Delay must have a deterministic fallback tempo when host tempo is unavailable. Transport observation remains shell-owned; DSP receives only sanitized values.

Activation generations must own effect state and tails

The existing core already lets old voices finish against an older render model after a new activation arrives. DSP introduces the same requirement for stateful chains. The unit of retirement must become a complete render generation: immutable model + compiled graph + mutable effect state + scratch ownership.

On activation

  1. The new generation becomes the only destination for new note-ons.
  2. Existing voices continue through the graph generation they started with.
  3. The old graph continues only while it has old voices or an audible bounded tail.
  4. When both conditions end, audio enqueues the existing style of primitive retirement token.
  5. Message-owned service destroys the generation and releases prepared ownership.

Bounded policy

  • Reuse the activation-slot capacity as the initial hard generation bound.
  • Each effect declares a maximum tail class; infinite feedback is clamped below unity.
  • A silence detector may retire earlier, but a hard time/frame ceiling guarantees reclamation.
  • Under pressure, use an explicit oldest-generation fade-out and diagnostic counter—never unbounded retention.
  • reset/panic clears voices and effect state; normal note-off and all-notes-off allow tails.

Preview semantics

Selected-zone preview should hear that zone’s chain, its owning group chain, and the instrument chain. Selected-group preview should hear member-zone chains, the group chain, and the instrument chain. Preview and Performance run equivalent graphs in isolated contexts and are summed only after each lane completes. This keeps authoring WYSIWYG without sharing delay lines or reverb state with the published instrument.

Schema and migration

The natural next project revision is project schema 5 / authoring schema 4. The exact number should be frozen with the implementation plan, but the migration behavior should be decided now.

Version 4 → DSP-capable version

  1. Map legacy short types such as eq, delay, reverb, chorus, and saturator to catalog IDs and versioned defaults.
  2. Canonicalize bare zone source IDs to zones/<id>; retain groups/<id> and master.
  3. Validate one bus per source and one owner per slot. Resolve legacy ambiguity deterministically and emit findings.
  4. Treat group.routingBusId as migration guidance, then derive new ownership from the bus source.
  5. Preserve all original IDs and chain order where valid.

Preserve legacy sound

Existing FX metadata has never affected rendered audio. Therefore every migrated legacy slot should initially be runtime-bypassed and marked “review to enable,” even if its old metadata said bypassed: false. A creator can enable it deliberately after hearing the result.

This is the only migration that guarantees a pre-DSP project sounds identical immediately after loading.

State and digest impact

  • Host-state budgets already allow 128 FX slots and 128 routing buses. Add parameter-count, parameter-string, aggregate delay-memory, and compiled-cost limits.
  • Snapshot content digest must include effect type/version, bypass, every parameter value, owner source, and exact chain order.
  • Prepared content and publish conformance need a DSP graph digest in addition to route, source-provenance, and macro-schema digests.
  • Preset state continues to store macro values; project/host state stores authored DSP topology and defaults. Runtime delay lines and reverb histories remain transient and are never serialized.

Verification strategy

Contract

  • Unknown type/version behavior
  • Parameter ranges and defaults
  • One chain per owner
  • No shared/orphan slots
  • Deterministic digest and migration

DSP

  • Golden impulse/step/sine vectors
  • Slot-order non-commutativity
  • Zone/group/master isolation
  • Bypass and smoothing clicks
  • Tail duration and silence bounds

Real-time

  • No allocation or locks in callback
  • Generation activation soak
  • Scratch/memory budget rejection
  • Worst-case block timing
  • Denormal and NaN containment

Product behavior

  • Selected-zone and selected-group preview hear the correct ancestors.
  • Preview and Performance effect states remain isolated.
  • Save/reload and host recall reproduce authored defaults and macro mappings.
  • Legacy projects remain audibly unchanged after migration.

Matrix

  • 44.1, 48, 88.2, and 96 kHz
  • Small, typical, and maximum supported block sizes
  • Mono and stereo host output
  • Editor open/closed and standalone/VST3
  • Warm/cold preparation and rapid publish replacement

Decisions to freeze before implementation

✓

Use one serial insert chain per zone, group, and instrument. Aux sends, bus-to-bus routing, feedback, and sidechains are later features with separate graph semantics.

✓

Process zone effects after zone voices are summed. Reverb and delay are shared by the zone, not multiplied by voice count.

✓

Preserve current route gain/pan math in the first vertical slice. The compiled graph changes destinations, not existing dry-level behavior; effect-specific gain remains explicit in the chain.

✓

Put mutable effect state in a bounded activation generation. Old voices and tails retain their generation until safe message-thread retirement.

✓

Keep host automation macro-based. Compile stable slot/parameter targets into the existing fixed macro callback topology.

✓

Make the public DSP contract product-owned. Library primitives are implementation details; arbitrary plug-in hosting and HISE-owned graph state are out of scope.

Options considered

ApproachFitReason
Direct effect fields on every zone/group/project Reject Fast for one reverb, but duplicates schemas, limits ordering, weakens stable macro identity, and becomes brittle as the catalog grows.
Per-voice DSP chain Reject Useful only for genuinely voice-local filters/envelopes. Reverb and delay state multiply with polyphony and do not produce normal shared-bus behavior.
Unrestricted node graph Defer Powerful, but it introduces cycles, latency alignment, sends, feedback, graph scheduling, and much harder creator UX before the requested three scopes work.
HISE-owned DSP graph now Reject now HISE integration is currently disabled, while the product-owned sampler core already owns rendering, activation, preview/performance isolation, and real-time diagnostics.
Compiled hierarchical insert graph Recommend Reuses the authored bus seam, matches the current immutable activation pipeline, is bounded on audio, and directly expresses zone → group → instrument processing.
