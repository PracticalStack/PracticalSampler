Outcome and boundaries

Creator outcome

An author can create up to twelve exposed controls, publish once, and immediately verify the same labels and ordering in Perform.

Player outcome

Perform shows a compact mixer with readable source labels, parameter labels, values, and control semantics without exposing helper macros.

Host outcome

DAWs see one stable parameter topology. Project edits may rebind slots, but may never add, remove, or reorder host parameters.

Iteration boundary: support twelve visible controls now, backed by sixteen permanent host slots. The remaining four slots are capacity for hidden helpers and compatibility. Do not ship a four-slot intermediate topology.

Current defect and evidence

Confirmed user scenario

  • The saved project contains 3 groups, 3 group-owned Gain inserts, and 3 macros.
  • All 3 macros are marked exposedInPerformance.
  • Two exposed macros publish and render; the third prevents activation.
  • The Plucks macro currently targets mute, not gainDb; that is a separate authoring correction.

Root cause

  • maximumPublishedMacroHostSlots declares 16.
  • The actual parameter layout is generated from the two reference macros.
  • Published host slots are also generated from those same two reference macros.
  • A third exposed macro produces published-macro-exposed-slot-missing.
  • The activation rejection loses the detailed finding and does not reliably refresh the UI presentation.
Product consequence: the current UI allows authors to create a valid-looking configuration that the runtime cannot activate, and then fails to explain the mismatch. Capacity enforcement and failure presentation must become part of the same contract.

Architecture decisions to freeze

1. One fixed topology

Create exactly sixteen host parameters when the processor is constructed. The topology is defined by product code, never by the loaded reference manifest or current authored project.

2. Preserve compatibility IDs

Retain macro.tone and macro.motion as the first two host IDs. Add stable generic IDs for slots 3 through 16. Never recycle a host parameter ID for a different slot.

3. Twelve visible, sixteen total

Allow at most twelve exposed controls and at most sixteen authored macros total. Exposed controls receive slots first; hidden helpers use the remaining capacity.

4. Authored identity is separate

A published binding maps an authored stable ID to a fixed host slot. Rename and reorder preserve the binding; delete retires it; a newly added control receives an available slot deterministically.

5. Presentation stays off audio

Labels, section names, units, control type, and ordering are immutable publication metadata prepared on the message/worker side. The audio callback consumes only the existing primitive slot view.

6. Last-known-good remains audible

A failed publication must leave the active generation untouched, report the exact failure, and allow a corrected draft to publish without restarting DRS or the host.

Target mixer UX

Expanded layout

  • Four controls per row; up to three rows.
  • Group/source label above the authored control name.
  • Vertical fader for gain, knob for continuous non-gain parameters, toggle for boolean parameters.
  • Persistent value and unit text below each control.
  • Authored order is preserved left-to-right, top-to-bottom.

Compact layout

  • Two controls per row inside a bounded viewport.
  • No label truncation without a tooltip or accessible full name.
  • Status/diagnostic copy must not consume mixer space when healthy.
  • Keyboard traversal follows visible order; hidden controls are absent from focus.
  • An empty state explains whether no controls are exposed or Publish failed.

Contract and red tests

Freeze behavior before changing topology

Turn the discovered two-slot defect into a permanent regression and define the compatibility rules that every later sprint must preserve.

Development tasks

  • PM0.1 Add a product constant for 12 exposed controls, distinct from the existing 16 total host slots.
  • PM0.2 Define the complete ordered host-slot table, including compatibility IDs for Tone/Motion and stable IDs for slots 3-16.
  • PM0.3 Add a three-layer project fixture modeled on Bell, EPiano, and Plucks with three group-owned Gain inserts and three exposed macros.
  • PM0.4 Add red binding tests for 3, 12, and 16 authored macros plus 13 exposed and 17 total overflow cases.
  • PM0.5 Add red processor integration coverage proving parameter count/order/IDs do not change across project load, edit, publish, close, and restore.
  • PM0.6 Add a red shell test requiring the detailed published-macro-exposed-slot-missing failure to appear in both standalone and plug-in surfaces.
  • PM0.7 Record the compatibility policy in a focused contract document and link it from the existing Sprint 6 macro automation contract.

Exit gate

  • Every intended behavior has a named failing test.
  • Failures demonstrate the two-slot defect, not fixture or loader errors.
  • Slot IDs and ordering are explicitly approved before implementation.

Primary files: PublishedMacroBinding.h, Sprint6PublishedMacroBindingTests.cpp, new topology contract tests, tests/CMakeLists.txt, and docs/phase1-sprint6-published-macro-automation.md.

Fixed 16-slot host topology

Make twelve controls technically possible

Remove the reference manifest from topology ownership and make one canonical slot definition drive parameter construction, binding, listeners, state, and callback views.

Development tasks

  • PM1.1 Introduce a shared immutable PublishedMacroHostTopology definition with 16 ordered slots.
  • PM1.2 Change Processor::buildParameterLayout to instantiate the shared topology instead of iterating EngineFacade::getMacroDescriptors().
  • PM1.3 Change initializePublishedMacroRealtimeState to initialize all 16 slots, listeners, atomic values, sequence baselines, and inactive callback entries.
  • PM1.4 Change EngineFacade::buildPublishedHostSlots to consume the shared topology rather than referenceManifest.instrument.macros.
  • PM1.5 Keep authored stable IDs separate from host parameter IDs throughout binding, parameter-change dispatch, and descriptor generation.
  • PM1.6 Preserve deterministic slot retention across rename, reorder, hide/unhide, delete/re-add, and republish.
  • PM1.7 Ensure inactive slots are neutral and cannot affect DSP, voice behavior, diagnostics, or displayed controls.
  • PM1.8 Prove slot installation remains a bounded primitive copy with no allocation, lock, or shared-ownership release on the audio thread.

Exit gate

  • Three and twelve exposed controls publish and activate.
  • Sixteen total bindings remain supported within the fixed callback view.
  • Host parameter count, IDs, and order remain identical through all project operations.
  • Existing two-macro sessions retain their first two parameter IDs.

Primary files: PluginProcessor.cpp/.h, EngineFacade.cpp/.h, PublishedMacroBinding.cpp/.h, PerformancePublishController, and host parameter contract tests.

Publication truth and recovery

Never fail silently

Move capacity and target failures into actionable preflight where possible, and make every later activation failure update the immutable presentation snapshot immediately.

Development tasks

  • PM2.1 Add publish preflight for more than 12 exposed controls, more than 16 total macros, invalid target identity, missing DSP control, duplicate ID, and invalid range/default.
  • PM2.2 Preserve the most specific binding finding instead of replacing it with generic performance-macro-binding-rejected.
  • PM2.3 On every authorization failure, update transient status, diagnostics, publish presentation, and engine state revision exactly once.
  • PM2.4 Show failure code, affected macro label, capacity count, and repair guidance in both Map and Perform.
  • PM2.5 Keep the last-known-good generation and binding table active after a rejected replacement.
  • PM2.6 Allow a corrected draft to retry immediately without reopening the project, restarting audio, or changing unrelated controls.
  • PM2.7 Add diagnostic counters for exposed, hidden, assigned, unassigned, available-slot, and active-slot counts.
  • PM2.8 Add shell parity, duplicate request, supersede, cancellation, and failed-then-successful recovery tests.

Exit gate

  • A 13th exposed control is rejected before activation with exact repair guidance.
  • Perform never claims Active for a failed revision.
  • Last-known-good audio and controls remain usable.
  • A valid retry becomes Active without application restart.

Primary files: EngineFacade.cpp, PerformancePublishPresentation.cpp, PerformancePublishController.cpp, PerformancePanel.cpp, AuthoringPanel.cpp, and Sprint 6 recovery/shell tests.

3

Published presentation model

Give the UI trustworthy labels and semantics

Publish enough immutable metadata for a concise mixer without coupling UI layout to mutable authoring structures or inspecting DSP descriptors during rendering.

Development tasks

  • PM3.1 Define a lightweight PublishedMacroPresentation record: authored label, section/source label, parameter label, value unit, control kind, order, and accessibility description.
  • PM3.2 Derive source labels from DSP ownership: group display name for group buses, zone name for zone buses, and Instrument for the global bus.
  • PM3.3 Derive control kind and unit from curated DSP descriptors: gain fader/dB, boolean toggle, and continuous knob or fader for other parameters.
  • PM3.4 Preserve authored macro order as the default visible order; do not alphabetize or order by host slot.
  • PM3.5 Carry presentation metadata in the immutable published binding table or a revision-matched companion snapshot.
  • PM3.6 Extend EngineMacroDescriptor so Perform never reconstructs source ownership from the mutable project.
  • PM3.7 Define deterministic fallback labels for deleted/legacy metadata and keep malformed presentation hints non-fatal to audio publication.
  • PM3.8 Add serializer/migration support only if presentation overrides are persisted; otherwise document that Sprint 3 labels are derived.

Exit gate

  • The active descriptor set is sufficient to render all labels and control types.
  • Group renames appear only after Publish and preserve slot identity/value.
  • No UI code walks mutable authoring routing or FX collections.
  • No presentation formatting runs on the audio callback.

Primary files: PublishedMacroBinding.h/.cpp, PlaybackSnapshot.h/.cpp, EngineFacade.cpp, curated DSP descriptors, runtime serializers if needed, and presentation-model tests.

Risks and non-goals

Primary risks

  • Must control Adding host parameters can affect DAW compatibility if the first two IDs or ordering change.
  • Must control Slot mapping must be installed atomically with the audio generation.
  • Must control Dynamic authored labels cannot become dynamic host parameter topology.
  • Should control Twelve labeled controls can overwhelm the current panel without viewport and status compaction.
  • Should control Derived group labels can become ambiguous when several controls share one owner.

Explicit non-goals

  • Later Arbitrary drag-and-drop control placement.
  • Later Creator-defined colors, artwork, themes, or freeform panels.
  • Later More than twelve player-facing controls.
  • Later Nested pages or user-authored section hierarchy.
  • Later Runtime mutation of host parameter count, IDs, or ordering.

Iteration definition of done

  • The original three-layer project publishes all three corrected gain controls and renders them in Perform.
  • A twelve-control instrument renders in a readable four-column expanded grid and a reachable two-column compact grid.
  • The processor exposes one stable 16-slot host topology independent of loaded content.
  • Old Tone/Motion automation remains compatible, while new authored IDs bind deterministically to the remaining slots.
  • Thirteen exposed controls fail before activation with actionable capacity guidance; no failure is silent.
  • Save/reload, host recall, replacement Publish, automation, realtime safety, and both application shells pass their release gates.
