Velocity Crossfade Authoring Development Plan

Add a safe, visual workflow for creating and editing the linear velocity crossfades already supported by the runtime. The UI will treat each crossfade as one relationship between adjacent velocity layers, update both zones atomically, and prevent authors from committing mismatched metadata.

Target outcome

What authors will be able to do

Create

Select two compatible velocity layers—or an ordered stack—and create valid overlaps with a chosen width.

Edit

Change an overlap numerically in the Sample inspector or drag its handles directly in the Zone Map.

Understand

See fade direction, overlap range, partner zone, eligibility problems, and resulting playback behavior without reading manifest JSON.

Scope decision

This plan delivers linear velocity crossfades between adjacent compatible layers. Key crossfades, CC crossfades, equal-power/custom curves, arbitrary many-way blends, and compiled-instrument export remain out of scope.

Starting point

What already exists

Runtime and persistence are ready

  • VelocityCrossfadeDescriptor stores fade-in, fade-out, and curve metadata.
  • First-pass validation requires complete, ordered windows and a linear curve.
  • Partner discovery and runtime topology already detect missing, ambiguous, and Round Robin-invalid relationships.
  • Project and instrument manifests preserve valid crossfade metadata.
  • Prepared playback and voice mixing already apply deterministic crossfade gains.
  • Supported SFZ velocity crossfades import into native metadata.

The authoring gap

  • The Zone selector only exposes existing metadata as debug text.
  • ZoneFieldValuesViewModel has no crossfade fields or eligibility state.
  • ZoneMappingEditor has no crossfade section, values, actions, or partner status.
  • ZoneMapCanvas draws velocity rectangles but no fade bands or fade handles.
  • Zone velocity edits can change boundaries without explicitly coordinating linked crossfade endpoints.
  • No author-facing transaction creates or removes both sides of a pair atomically.

Core modeling problem

A crossfade is serialized twice: the lower layer owns a matching fade-out window and the upper layer owns a matching fade-in window. Exposing those as four independent fields would make invalid states easy to create. The authoring API must accept a relationship edit and materialize both zone descriptors in one validated transaction.

Product behavior

Recommended author workflow

1. Select layersSelect two compatible zones or a complete velocity stack.
2. Check eligibilityUI explains key, articulation, trigger, or Round Robin mismatches.
3. CreateChoose Create Crossfade and a default or explicit overlap width.
4. ShapeDrag shared overlap handles or enter exact low/high velocities.
5. AuditionPreview below, inside, and above the overlap.
6. SaveUndo/redo and project round-trip preserve the paired edit.

Single-zone inspector

Show Fade In and Fade Out rows separately, each with partner name, active overlap range, Edit, and Remove. The curve is shown as “Linear” and is not editable in this phase.

Multi-selection inspector

For compatible layers, show Create Crossfades, overlap width, and Remove Crossfades. Avoid displaying a misleading single mixed value when selected relationships differ.

Compatibility identity

Eligible partners must share articulation, root key, key range, and trigger mode. Non-Round-Robin zones pair only with non-Round-Robin zones. Round Robin layers must use the same pool shape and matching slot position; edits must be repeated consistently across every slot bundle.

1

Crossfade authoring contract

Engine + session · no UI dependency

Create one source of truth for partner eligibility and mutation planning before exposing controls.

  1. XF-1.1 Define request/result types for create, resize, and remove operations. Include selected zone IDs, direction or pair IDs, requested overlap low/high or width, affected zone IDs, warnings, and blocking issues.
  2. XF-1.2 Extract or reuse the runtime pairing-key rules so authoring eligibility matches playback identity exactly: articulation, root, key range, trigger mode, and Round Robin identity.
  3. XF-1.3 Implement deterministic partner discovery. Return explicit states for eligible, missing partner, ambiguous partner, incompatible mapping, incomplete RR pool, mixed slot count, and duplicate slot.
  4. XF-1.4 Implement an atomic pair planner. For overlap [L,H], set lower velocityHigh=H plus fade-out [L,H], and upper velocityLow=L plus fade-in [L,H].
  5. XF-1.5 Re-run validateFirstPassVelocityCrossfadeZone, pair validation, and full topology validation against the proposed project before committing.
  6. XF-1.6 Add AuthoringSession commands for pair create/update/remove, each producing exactly one undo snapshot and precise changed paths.
  7. XF-1.7 Define ordinary velocity-edit behavior for crossfaded zones. Route affected edits through the planner so owned outer endpoints stay synchronized; reject edits that would overlap a zone's fade-in and fade-out windows.
  8. XF-1.8 Add unit coverage for valid pairs, boundary velocities 1 and 127, minimum two-step windows, inverted windows, missing/ambiguous partners, paired removal, undo/redo, and no-op edits.

Sprint exit gate

A test can create, resize, remove, undo, and redo a crossfade exclusively through AuthoringSession. No operation can leave only one side of a pair or persist an invalid topology.

Likely files: engine_adapter/include/drs/engine/VelocityCrossfade.h, new VelocityCrossfadeAuthoring.h/.cpp, AuthoringSession.h/.cpp, new Phase3CrossfadeAuthoringTests.cpp, tests/CMakeLists.txt.

2

Sample inspector workflow

Exact values + explicit actions

Deliver a complete, accessible numeric workflow before adding canvas gestures.

  1. XF-2.1 Add crossfade view models describing Fade In, Fade Out, partner ID/name, overlap low/high, curve label, eligibility, mixed multi-selection state, and blocking guidance.
  2. XF-2.2 Extend AuthoringPanel::buildZoneFieldValuesViewModel to derive author-facing relationship state from the current project rather than trusting debug strings.
  3. XF-2.3 Add a collapsible “Velocity Crossfades” subsection under Sample inspector with stable component IDs and focus order.
  4. XF-2.4 For a selected zone, render Fade In and Fade Out status independently: partner label, overlap range, Linear curve label, Edit, and Remove.
  5. XF-2.5 For an eligible two-zone selection, show Create Crossfade and an overlap-width/range control. Disable the action with a plain-language reason when mappings cannot pair.
  6. XF-2.6 Commit numeric edits only on slider end, Return, or focus commit—not on every intermediate text change. Keep one user gesture equal to one undo entry.
  7. XF-2.7 Normalize harmless input ordering, but do not silently choose a different partner or silently remove metadata. Show validation errors adjacent to the controls.
  8. XF-2.8 Replace or supplement Zone-selector debug text with concise user-facing crossfade status while retaining enough diagnostic detail for imported content.
  9. XF-2.9 Add component, callback, layout, accessibility, focus, compact-shell, expanded-shell, and undo/redo tests.

Sprint exit gate

An author can select two zones, create a crossfade, enter an exact overlap, inspect both partners, remove it, and undo every step without using the Zone Map.

Likely files: AuthoringViewModels.h, ZoneMappingEditor.h/.cpp, CompactInspectorPrimitives.* if a new row is needed, AuthoringPanel.h/.cpp, Phase2AuthoringUiTests.cpp.

3

Zone Map visualization and gestures

See it · drag it · cancel it

Make overlap behavior legible and directly manipulable without confusing crossfade handles with ordinary velocity-range handles.

  1. XF-3.1 Draw fade-in and fade-out bands inside zone rectangles using opposing vertical gradients and distinct outlines. Ensure paired bands align to the same MIDI velocities.
  2. XF-3.2 Add a compact legend or contextual label for Fade In, Fade Out, and the numeric overlap. Preserve zone labels and selection contrast.
  3. XF-3.3 Extend RangeHandle or introduce a dedicated crossfade-handle type for overlap low/high. Give crossfade handles distinct geometry and hit-testing priority.
  4. XF-3.4 Build a crossfade gesture object containing both original partner zones, the proposed pair edit, preview topology, and validation state.
  5. XF-3.5 During drag, preview both zones and both gradients. Clamp to 1–127, preserve low < high, and prevent a zone's Fade In and Fade Out windows from touching or crossing.
  6. XF-3.6 Commit through the Sprint 1 relationship API; never send independently edited summaries from the canvas. Escape/right-click/focus loss must cancel without a transaction.
  7. XF-3.7 Add keyboard adjustment for a focused crossfade handle using arrows, Shift for larger steps, and accessible value text such as “Fade out overlap 45 through 60 with Layer 3.”
  8. XF-3.8 Verify rendering and hit testing at zoom levels 1×–8×, with overlapping rectangles, multiple selection, clipped viewport edges, and compact host sizes.
  9. XF-3.9 Add screenshot/paint characterization plus gesture commit, cancellation, clamping, one-undo, and inspector-synchronization tests.

Sprint exit gate

Existing crossfades are visually unmistakable, and dragging either overlap boundary updates both partners live and commits one valid undoable transaction.

Likely files: ZoneMapCanvas.h/.cpp, AuthoringPanel.cpp, Phase2AuthoringUiTests.cpp, optional new VelocityCrossfadeUiTests.cpp.

4

Layer-stack and Round Robin authoring

Useful at instrument scale

Turn pair editing into a practical workflow for real sampled instruments with many velocity layers and RR slots.

  1. XF-4.1 Define deterministic layer ordering by effective velocity range, with stable ID as a diagnostic tie-breaker only. Reject ambiguous duplicate layers instead of guessing.
  2. XF-4.2 Implement Create Crossfades for N selected compatible layers, producing exactly N−1 adjacent relationships.
  3. XF-4.3 Define the default overlap algorithm around each seam. Preserve stack endpoints 1 and 127, clamp requested width, and use deterministic integer rounding.
  4. XF-4.4 Provide a preview summary before commit: layer order, generated overlap ranges, clamped widths, and zones that will change.
  5. XF-4.5 Support Remove Crossfades Across Selection without modifying unrelated velocity ranges. Offer a separate explicit “restore hard splits” action only if product behavior is defined and tested.
  6. XF-4.6 Group RR zones by slot and require complete slot coverage. Apply identical crossfade shapes to every slot so runtime topology remains deterministic.
  7. XF-4.7 Prevent ordinary multi-zone velocity edits from partially breaking a stack. Either plan the complete linked update or reject it with an explanation and a direct “Edit Crossfades” route.
  8. XF-4.8 Add tests for 2, 5, and 10 velocity layers; unequal existing ranges; boundary clamping; gaps; pre-existing overlaps; partial selections; RR pools with 2–4 slots; and mixed/incomplete RR selections.

Sprint exit gate

A ten-layer selection creates nine valid crossfades in one undoable operation. Complete RR bundles receive matching shapes; incomplete or ambiguous bundles explain why creation is unavailable.

Likely files: crossfade authoring planner, AuthoringSession, AuthoringPanel, ZoneMappingEditor, new stack/RR authoring tests.

5

Audition, persistence, and release hardening

End-to-end confidence

Close the loop from authored relationship to audible result and durable saved content.

  1. XF-5.1 Add an overlap audition action that triggers velocities immediately below, at the low edge, at the midpoint, at the high edge, and immediately above the crossfade.
  2. XF-5.2 Surface expected partner contribution or a simple lower/upper gain readout during preview, using the same runtime gain function rather than UI math.
  3. XF-5.3 Ensure authoring edits invalidate and rebuild draft playback through the existing prepare/publish contract. Confirm no stale runtime topology remains after resize or removal.
  4. XF-5.4 Extend persistence tests to cover UI-authored pairs and stacks through project save/load and companion instrument-manifest generation.
  5. XF-5.5 Verify imported supported SFZ crossfades open as editable relationships, survive a no-op save exactly, and can be resized without losing partner/RR identity.
  6. XF-5.6 Add negative tests for unsupported imported shapes. Display them as preserved/read-only or review-required; never silently rewrite them into supported linear shapes.
  7. XF-5.7 Run compact/expanded layout, keyboard-only, screen-reader text, contrast, high-DPI, zoom, undo/redo, save/reload, and DAW-host smoke gates.
  8. XF-5.8 Update author documentation with a two-layer walkthrough, stack workflow, RR rules, limitations, and troubleshooting messages.

Sprint exit gate

An author can create a crossfade, hear the overlap, save the project, reload it, prepare/publish playback, and obtain the same relationship and audible behavior in both standalone and plug-in shells.

Likely files: preview command/controller code, ProjectStorage tests, crossfade prepared-playback tests, SFZ projection tests, authoring UI tests, documentation.

Release gate

Definition of done

Functional

  • Create, edit, remove, undo, and redo a pair.
  • Create N−1 relationships for an N-layer stack.
  • Edit numerically and by Zone Map drag.
  • Preserve complete RR topology.
  • Audition the overlap through runtime behavior.

Quality

  • No invalid or half-authored relationship can commit.
  • One user gesture equals one undo transaction.
  • Compact and expanded shells remain usable.
  • Keyboard and accessibility semantics cover every action.
  • Project/instrument round-trip and imported SFZ regressions pass.

Recommended first implementation slice

Complete Sprint 1 and the two-zone portion of Sprint 2 before beginning Zone Map visuals. That produces a safe, testable authoring feature early and prevents canvas code from becoming the owner of crossfade rules.
