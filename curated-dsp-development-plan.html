Engineering roadmap · design-to-delivery

Curated DSP implementation plan

An 18-sprint development sequence that grows the existing FX metadata into a compiled, real-time-safe zone → group → instrument processing system, then delivers gain, saturation, stereo delay, algorithmic reverb, compact EQ/filter, and chorus.

Execution recommendation

Ship the infrastructure before the expensive effects. The first eight sprints establish schema, validation, graph compilation, activation ownership, dry-path parity, scoped routing, and a smoothed control plane. Only then add saturation, delay, and reverb. This prevents each effect from inventing its own lifecycle, routing, parameter, and recall behavior.

Cadence assumption: each item is a focused mini-sprint, usually about one engineering week for one primary developer plus review. Sprints may be combined when capacity allows, but their exit gates should remain separate. S0–S15 form the Wave 1 release path; S16–S17 are Wave 2 catalog expansion.

Non-negotiable engineering constraints

No allocation, locks, file access, JSON, string construction, or object destruction in the audio callback.
No-DSP projects retain the current direct fast path and dry output.
One serial insert chain per zone, group, or instrument owner.
Preview and Performance never share mutable DSP state.
DSP topology is immutable per activation generation.
Parameter values may change without rebuilding topology.
Legacy schema-4 FX metadata remains audibly inert until reviewed and enabled.
Only fixed published macros become DAW-visible parameters.
Unknown effect types/versions are preserved, reported, and bypassed.
Every effect has a versioned algorithm, bounded memory, bounded tail, and deterministic reset.

Wave 1 scope

  • Zone, group, and instrument inserts
  • Gain/trim, saturator, stereo delay, algorithmic reverb
  • Live creator parameters and macro automation
  • Save/reload, host recall, undo/redo, publish, preview
  • Mono/stereo output and common sample-rate/block-size matrix

Explicitly deferred

  • Aux sends, sidechains, feedback routing, or bus-to-bus graphs
  • Third-party VST/AU hosting
  • Convolution reverb and impulse-response asset management
  • Oversampling and host latency compensation
  • Dynamic publication of every effect parameter to the host

Milestone gates

G0 · Contract ready

After S0: ADR, budgets, red tests, compatibility recordings, and schema decisions are reviewed.

G1 · Data ready

After S3: projects, snapshots, prepared identity, digests, and migrations are deterministic.

G2 · Renderer ready

After S7: no-DSP output is unchanged and zone/group/instrument gain works through one graph.

G3 · Automation ready

After S9: live values, bypass, macros, host automation, preview, and publish share one target system.

G4 · Wave 1 sound ready

After S12: saturation, delay, reverb, reset, tails, transport, and pressure retirement are bounded.

G5 · Product ready

After S15: UX, recall, migration, CPU/memory, offline baselines, and host validation pass.

Expected existing-file responsibilities

  • RuntimeModel.h — authored slot parameters, algorithm versions, and bus ownership fields.
  • RuntimeLoader.cpp — schema 5 / authoring 4 serialization, validation, and schema-4 migration.
  • AuthoringSession.* — undoable slot/chain/parameter transactions and stable changed paths.
  • PlaybackSnapshot.* — full immutable DSP capture and authored graph digest input.
  • PreparedPlayback.* — prepared graph plan, cost/memory findings, and DSP conformance digest.
  • SamplerRenderModel.* — route destination indices and immutable graph plan reference.
  • SamplerVoicePool.* — accumulate voices into precompiled graph destinations.
  • SamplerPlaybackContext.* — mutable generation state, execution, tails, and retirement.
  • PublishedMacroBinding.* — structured DSP parameter targets and bounded callback bindings.
  • PluginProcessor.* — sanitized transport view and shell-to-core parameter handoff.
  • AuthoringPanel.* — scope-aware chain editor and curated parameter panels.
  • HostSessionState.* — structural budgets and complete authored DSP recall.

Proposed new modules

Names are provisional; ownership is the important part.

  • CuratedDspCatalog.* — type/parameter/version/cost descriptors.
  • DspGraphPlan.* — normalized nodes, routes, scratch plan, and compiler findings.
  • DspRenderGeneration.* — exclusive mutable state and processing lifecycle.
  • DspParameterControl.* — bounded updates, target resolution, and smoothing metadata.
  • DspGain.*, DspSaturator.*, DspStereoDelay.*, DspAlgorithmicReverb.* — versioned kernels.
  • DspCompactEq.*, DspChorus.* — Wave 2 kernels.
  • CuratedDspChainEditor.* — reusable zone/group/instrument creator surface.

Definition of done for every sprint

The sprint’s focused tests are green and registered with CTest.
The target is included in drs_all_tests when the slice becomes authoritative.
No unrelated user changes in the dirty worktree are overwritten.
New schema fields and findings have stable names and documented ownership.
Audio-thread changes pass realtime guard and bounded-storage review.
Deterministic serialization/digest tests cover every new persistent value.
Preview and Performance behavior is tested independently when runtime-facing.
Diagnostics are primitive snapshots; UI never reads mutable engine state.
Failure leaves the previous valid project/activation available.
Sprint evidence and any deferred debt are added to the project documentation.
Final completion condition: the feature is not complete merely when effects make sound. It is complete when authored topology, preview, publish, automation, save/reload, VST3 recall, migration, tails, performance budgets, and failure recovery all agree on the same versioned graph.
