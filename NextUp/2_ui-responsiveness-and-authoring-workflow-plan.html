UI Responsiveness and Authoring Workflow Plan

Practical Sampler · High-level implementation and qualification plan

Working diagnosis: the remaining problems are message-thread bottlenecks, not failures in the streaming or audio-rendering path. Host MIDI, playable-package export, and playable-package import are already performing well and must remain protected throughout this work.
Overall status: Complete and cross-phase qualified 2026-08-11. All five phases are implemented and validated against the 1,700-zone/637-source Salamander project and the playable-package regression fixture.

Goals

  • Make the Performance tab immediately responsive to keyboard and control input.
  • Make zone selection and ordinary authoring navigation feel instantaneous at large-instrument scale.
  • Restore reliable Preview, Prepare Draft, and Publish workflows without blocking the UI.
  • Preserve the qualified package-loading, streaming, host-MIDI, and real-time behavior.

Guiding Design Rules

  • The message thread handles input, lightweight state changes, and presentation only.
  • Project validation, full-project copying, digests, serialization, and playback preparation must not run synchronously from routine UI interactions.
  • Selection is transient workspace state, not an authored-content edit.
  • UI refreshes are revision-aware and incremental rather than periodic full rebuilds.
  • Worker results are published as immutable snapshots and adopted without waiting.
  • Superseded preview and preparation requests are coalesced or canceled.

Implementation Phases

Phase 2 — Restore Performance-tab responsiveness

Status: Complete and validated 2026-08-11.

Purpose: remove synchronous presentation work from the UI note path.

  • Make Performance keyboard note-on and note-off callbacks queue-only.
  • Remove full surface refreshes from note callbacks.
  • Stop forcing complete Performance and Diagnostics refreshes on every editor timer tick.
  • Refresh only when relevant publication or presentation revisions change.
  • Update control values without rebuilding the control layout when its structure is unchanged.

Implementation: Performance note callbacks now only normalize and enqueue note events. Shell and component timers use engine-state and publication-sequence revisions, with one initial reconciliation, instead of unconditional Performance and Diagnostics rebuilds. Published mixer value changes preserve lane identity and layout.

Validation: drs.ui.performance_responsiveness, drs.performance_mixer.ui, drs.phase2.performance_ui, drs.phase1.performance_package_host_validation, drs.phase1.realtime_safety, and drs.ui.responsiveness_baseline passed in Debug. On the real fixture baseline, an unchanged Performance refresh fell from 3.516 ms to below the report's 1 µs resolution; combined note-on/off callbacks measured 0.088 ms with zero callbacks at or above 1 ms; the queued note rendered on the next 512-sample block with peak 0.34669. The plug-in and standalone shells compiled successfully.

Phase 3 — Make authoring selection lightweight

Status: Complete and validated 2026-08-11.

Purpose: prevent navigation from behaving like a complete project edit.

  • Move selected zone and selected group into transient workspace-selection state.
  • Do not dirty the project, create an undo snapshot, increment the authored-content revision, invalidate playback, or rebuild host state when selection changes.
  • Create a selection-only presentation refresh for the inspector, summary, waveform request, and map highlight.
  • Reserve full list and zone-map reconstruction for actual structural project changes.

Implementation: Zone and group focus now live in a transient workspace-selection state with an independent revision. Selection actions acknowledge navigation without committing project snapshots, changing dirty/history metadata, or mutating the persisted manifest fields. Authoring timers reconcile document and selection revisions independently; zone/group navigation updates only selector/list focus, inspector and summary models, waveform state, drawer context, and the existing map highlight. Full list and zone-map data reconstruction remains on the authored-document path.

Validation: drs.phase2.authoring_foundation, drs.phase2.mapping_workspace, drs.phase2.zone_group_transactions, drs.sprint8.zone_group_hardening, drs.phase2.authoring_ui, and drs.ui.responsiveness_baseline passed in Debug. The real 1,700-zone Salamander selection measured 7.539 ms, below one 60 Hz frame, with document revision delta 0, undo-depth delta 0, no dirty-state change, no persisted selection-field change, no full Authoring refresh, and no host-state serialization. Artifact: build/vs2022-debug/tests/ui-responsiveness-baseline.json.

Phase 4 — Make Preview, Prepare, and Publish asynchronous

Status: Complete and validated 2026-08-11.

Purpose: ensure commands return immediately while preparation continues in the background.

  • Remove message-thread polling and sleep loops from authoring audition.
  • Retain a pending audition event and emit it after the requested preview becomes active.
  • Move full playback-snapshot construction, digests, validation, and publish preflight to worker-owned immutable input.
  • Expose clear queued, preparing, ready, active, canceled, and failed states in the UI.
  • Guarantee that rapid selection or repeated commands activate only the newest eligible request.

Implementation: Authoring audition no longer services the message loop, polls, or sleeps inside the command handler. Scoped note events remain pending until the exact requested Preview identity is active; an early note-off is retained and emitted after a bounded audible interval, and project/package lifecycle resets discard pending audition state. A bounded playback-snapshot worker now owns immutable project input and performs snapshot construction, content and macro digests, validation, scoping, and Publish macro preflight. Preview and Publish requests queue immediately, coalesce queued work by lane, prioritize Publish work, cancel superseded queued work, and reject stale completions by contract request identity. Existing typed controllers and presentations continue to expose queued, preparing, ready, active, canceled, superseded, and failed states. Preparation publishes its current phase and source ordinal so the Authoring UI reports progress such as Preparing sources 187/637. A Publish of the exact current full-draft Preview reuses that immutable snapshot, prepared graph, data sources, and source heads instead of reopening all WAV files; identity or revision drift falls back to an ordinary fresh preparation. Streaming source identity now retains both sample-source ID and normalized path, matching Publish conformance requirements. Exact active Publish duplicates remain no-op requests.

Validation: All ten drs.sprint5.* Preview tests and all eleven drs.sprint6.* Publish tests passed in Debug, including rapid coalescing, cancellation/recovery, scoped preparation, pending audition, shell parity, editor/project closure, last-known-good activation, macro preflight, scheduler pressure, and integration hardening. Corrective regression coverage verifies streaming-source Publish conformance, exact Preview payload identity reuse, and rendered audio from the authored Performance keyboard. drs.ui.responsiveness_baseline passed with the real 1,700-zone/637-source Salamander fixture: Preview dispatched in 0.430 ms, exposed per-source progress while preparing, and reached Ready in 7.783 seconds in Debug; Publish dispatched in 0.109 ms, reused the exact Preview build and prepared payload, and reached Active in 0.731 seconds without preparing 637 WAV heads again. The authored keyboard then rendered a nonzero next-block peak of 0.00311772. Both dispatches remained below the 16.667 ms frame budget and below the 1 ms slow-span reporting threshold. The newest scoped request alone reached activation during churn, stale same-revision scoped payloads were rejected, and the tested audio/streaming paths reported no dropped events, callback-budget failures, or real-time guard violations. Artifact: build/vs2022-debug/tests/ui-responsiveness-baseline.json.

Phase 5 — Decouple host-state publication

Status: Complete and validated 2026-08-11.

Purpose: keep full-project serialization out of interactive authoring operations.

  • Publish immutable project checkpoints to a background serializer.
  • Compute manifest digests and serialized host state away from the message thread.
  • Atomically replace the last completed serialized state.
  • Coalesce intermediate content revisions while preserving the newest valid state.

Implementation: Added a processor-owned host-state publication worker that receives immutable authored-project checkpoints plus small preset, binding, revision, dirty-state, published-checkpoint, or playable-package metadata. Manifest digest computation and JSON serialization now run exclusively on the worker. Submission retains one active request and one newest pending request; its completion mailbox retains at most the newest success and newest failure. The processor atomically replaces the last completed serialized state by monotonic request identity, never replaces it with a failed or stale completion, and leaves getStateInformation as an immediate copy of the last-known-good publication. Project, package, and preset-only publication share the same service, and worker shutdown joins safely. Prepared-playback content identity was also made deterministic across processor instances by excluding runtime ownership tokens, build IDs, and data-source generations from the persisted digest while retaining them in diagnostic serialization.

Validation: drs.host_state.background_publication passed a 101-revision burst with at least 99 queued checkpoints coalesced, one pending request maximum, a one-result newest-success mailbox, exact revision 101/project round-trip, ten additional undrained sequential publications without mailbox growth, and safe active-worker destruction. drs.host_state.project_recall, drs.phase1.state_recall, drs.phase1.macro_bridge, the full five-test drs.phase1.performance_package* suite, drs.performance_package.export_lifecycle, mixer host-state round-trip, WAV lifecycle I/O audit, restore stress, streaming reader/service, Sprint 4 real-time guard, Phase 1 real-time safety, republish-churn real-time, and Performance responsiveness all passed in Debug. A 10-cycle WAV editor/import/close/reopen/restore/unload stress run passed. On the real 1,700-zone Salamander fixture, drs.ui.responsiveness_baseline passed with background host-state serialization taking 2,437.774 ms while concurrent zone interaction took 0.078 ms; the message-thread host-state span remained below the 1 ms reporting threshold, the completed chunk round-tripped all 1,700 zones, and Preview/Publish dispatch remained below one frame. Artifact: build/vs2022-debug/tests/ui-responsiveness-baseline.json.

Delivery Sequence

  1. Responsiveness patch: instrumentation, queue-only Performance notes, revision-aware refresh, and removal of the blocking audition wait.
  2. Authoring scaling patch: transient selection state and incremental Authoring refresh.
  3. Background publication patch: asynchronous snapshot construction, publish preflight, digests, and host-state serialization.
  4. Qualification pass: large-project interaction, command supersession, editor lifecycle, host-state restore, and streaming regression coverage.

Acceptance Gates

  • Performance keyboard callbacks complete in under 1 ms; notes are heard on the next audio block.
  • Zone selection completes within one 60 Hz frame and does not change the authored-content revision or dirty state.
  • Prepare and Publish handlers return within one frame and expose asynchronous progress.
  • No routine editor timer or interaction operation blocks the message thread for more than one frame.
  • Rapid selection churn activates only the newest preview request.
  • Editor open, close, and tab switching remain responsive with the large reference instrument.
  • Playable-package export and import remain correct and fast.
  • Host MIDI playback, page streaming, audio callback behavior, and real-time safety qualifications remain unchanged.
Primary guardrail: do not redesign the working streaming path to solve these UI problems. Changes should reduce message-thread work and improve state publication while leaving the qualified audio and streaming architecture intact.

Status: all five implementation phases complete and individually validated; final cross-phase qualification is in progress.
