Engineering Implementation Plan | August 29, 2026

Offline Portable Performance-Package Protection

This plan realigns the completed V3 cryptographic foundation with the intended Practical Sampler product: anybody can publish and play portable packaged instruments without an account, activation, entitlement, or Practical Sampler service. Packaging is one-way through the normal product. Direct inspection, ordinary sample extraction, and package modification are resisted, while determined reverse engineering of the application remains explicitly outside the guarantee.

Product Decision and Security Promise

Portable and Offline

Any Practical Sampler user may export a package. The package may be copied and played by another compatible Practical Sampler installation without contacting Practical Sampler infrastructure.

Opaque and Read-Only

Packaged samples, project settings, artwork, mappings, and UI definitions are not exposed as ordinary files and cannot be edited through normal Practical Sampler workflows.

Cracking Is Out of Scope

A determined reverse engineer who extracts the application protection capability or patches the executable may eventually decrypt, forge, or extract content.

Approved package-recognition meaning: the V3 signature means “recognized, internally consistent Practical Sampler package.” It does not prove the identity of an author, establish ownership, or prove issuance by a controlled Practical Sampler publisher.
Defensible customer statement: Practical Sampler playable-instrument packages are encrypted, integrity-checked, and read-only. Samples, project definitions, artwork, and UI content are not exposed as ordinary files. Practical Sampler provides no ordinary mechanism to extract, convert, or modify packaged content. This protection is intended to deter inspection, extraction, and unauthorized modification; it is not impenetrable DRM and does not prevent runtime reverse engineering or audio recording.
Superseded assumption: the controlled-publisher and externally provisioned production-key requirements in the parent plan and completion addendum do not apply to this offline profile. They remain a possible future licensed-publishing architecture, not a release gate for portable community packages.

Application Protection Profile

  • A release-family wrapping secret is available to compatible Practical Sampler binaries in an obfuscated, application-contained form.
  • A separate application-contained signing capability produces the existing V3 detached signature locally and offline.
  • Immutable key IDs and lifecycle policy permit later key rotation while retaining supported historical readers.
  • Test and development profiles remain cryptographically and semantically separate from production.

Honest Trust Boundary

  • AEAD and signature validation stop direct byte editing, record substitution, and ordinary repacking.
  • Obfuscation raises reverse-engineering cost; it is not treated as cryptographic secrecy.
  • The shipped application necessarily contains enough capability to create and open community packages.
  • Once that capability is extracted, confidentiality and forgery resistance for this offline profile may be defeated.
Wire compatibility decision: retain the existing signingKeyId, signature suite, signature bytes, release-key ID, and wrapped content-key fields. Change their product interpretation through an explicit offline protection profile rather than silently reusing controlled-publisher terminology.

Realign the Security Contract

Complete

Make the product promise, code terminology, diagnostics, and release gates describe the offline portable profile accurately before changing key behavior.

Development tasks

  • OPP-P0-T1 Record the attacker boundary: ordinary file inspection and normal product workflows are in scope; deliberate binary patching, debugger-assisted extraction, runtime capture, and recovered application secrets are out of scope.
  • OPP-P0-T2 Replace “publisher authenticity,” “trusted publisher,” and equivalent origin claims with “recognized Practical Sampler package” and “package integrity” where the offline profile is used.
  • OPP-P0-T3 Inventory affected documentation, UI messages, telemetry categories, class comments, tests, and release gates; distinguish wire-format names from customer-visible security claims.
  • OPP-P0-T4 Freeze the product rules: anybody may publish, packages are portable, no account/network/activation is required, and packaging does not enforce ownership or prevent copying.
  • OPP-P0-T5 Preserve V3 key IDs and provider interfaces as extension points for a future licensed-instrument profile without implementing licensing now.

Validation

  • Review every security statement for consistency with an extractable application-contained capability.
  • Confirm no release gate still requires a hosted signer, entitlement service, machine binding, or publisher identity for the offline profile.
  • Confirm the revised contract does not weaken the AEAD, bounded-reader, plaintext-minimization, or read-only requirements.
  • Confirm DRSPKG3 remains byte-compatible unless implementation evidence proves a format change is unavoidable.
Primary artifacts: this plan, performance-package-content-protection-plan.html, completion addendum, key-operations runbook, V3 format specification, product copy, and security-related diagnostics.

Exit gate — complete

Product and engineering have one internally consistent offline security promise; controlled-publisher provisioning is explicitly removed from the portable-package release gate; future licensing remains a separate profile.

1

Build the Offline Application Key Profile

Complete

Provide portable package encryption and decryption without a server, account, activation record, installation-specific key, or source-visible production secret.

Development tasks

  • OPP-P1-T1 Define a production offline-profile ID, immutable wrapping-key ID, activation date, rotation state, and compatibility policy distinct from every test/development ID.
  • OPP-P1-T2 Add a release-only key-generation and code-generation step that accepts cryptographically random key material outside source control and emits obfuscated fragments for the supported production targets.
  • OPP-P1-T3 Implement an application-contained PackageReleaseKeySource that reconstructs the wrapping key only into SecureBuffer, validates the expected length and ID, and zeroizes temporary material.
  • OPP-P1-T4 Keep raw contiguous key bytes out of repository content, fixtures, command lines, ordinary build logs, diagnostics, crash fields, and package bytes; document that encoded fragments are intentionally present in release binaries and may be recovered by reverse engineering.
  • OPP-P1-T5 Support active, retired, and revoked offline wrapping-key IDs so new exports use one active key while supported historical packages remain readable according to policy.
  • OPP-P1-T6 Make release configuration fail closed when the offline profile is missing, malformed, uses a test ID, has duplicate IDs, or selects a retired/revoked key for export.

Validation

  • Round-trip packages between independent clean installations of the same release family with the network disabled (pending Phase 3 release qualification).
  • Verify identical projects receive fresh content keys and nonces and do not produce deterministic ciphertext (the implementation is connected; built-in-profile qualification remains pending).
  • Search source, fixtures, packages, logs, symbols, and build output for raw production-key canaries and test-key leakage.
  • Exercise active, retired, revoked, unknown, malformed, and unavailable key states.
  • Perform a synthetic rotation: new exports use the new ID, historical packages follow retention policy, and retired IDs cannot encrypt.
Expected code: PackageKeys.*, SecureBuffer.*, generated release-profile inputs, engine-adapter CMake, and PackageKeyLifecycleTests.cpp.
Validation evidence — 2026-08-29: the default (unconfigured) release target compiled and passed drs_package_key_lifecycle_tests; a temporary profile generated from three 32-byte secrets (active, retired, revoked) compiled and passed the same test; the generator rejected a reserved test identifier and the generated header did not contain the raw active-key canary. Full package export/load round-trip and fresh-ciphertext checks remain Phase 3 integration gates.

Exit gate — complete

The default build fails closed without a profile, while a temporary active/retired/revoked profile generated from 32-byte secrets compiled and passed the lifecycle test. Reserved test/development identifiers, duplicate IDs, contradictory metadata, revoked keys, malformed fragments, unknown IDs, and empty package identities are rejected; active and retired keys load for supported historical reads. The generated header contains XOR fragments rather than a raw contiguous key, and the documentation states that reverse engineering can recover the application capability.

Implement the Local Package-Recognition Signature

Complete

Retain V3’s canonical detached signature as a local recognition and integrity check without claiming publisher identity or requiring a controlled service.

Development tasks

  • OPP-P2-T1 Define a production recognition-signing key ID and separate application-contained signing capability; do not reuse the wrapping key or any test signing key.
  • OPP-P2-T2 Implement a local offline PackagePublisherSigningClient adapter that signs only canonical V3 input and returns the existing audit/result shape without a network dependency.
  • OPP-P2-T3 Retain the public verification key in the immutable trust configuration, but interpret membership as a recognized offline protection profile rather than a trusted author or publisher.
  • OPP-P2-T4 Preserve complete signature coverage over the canonical envelope, wrapped key, TOC, record identities, nonces, ciphertext, tags, and ordering.
  • OPP-P2-T5 Change customer-visible errors and telemetry from publisher-origin language to redacted recognized/corrupt/modified-package categories.
  • OPP-P2-T6 Update class comments and tests so existing wire names such as signingKeyId cannot be mistaken for author identity or a remotely trusted publishing authority.

Validation

  • Sign canonical in-memory V3 input with the network unavailable and no externally injected security context; full export/load wiring is a Phase 3 gate.
  • Reject unknown signing IDs, missing/ambiguous canonical input, and unconfigured signing profiles; existing V3 tests cover altered signatures, truncation, substitution, reordering, and cross-package mutations.
  • Confirm the local signer uses Ed25519ph over canonical bytes/files and returns only a redacted local audit identifier; no signing capability, wrapping keys, plaintext, nonces, or tags are logged.
  • Confirm documentation, class comments, and diagnostics use recognition/integrity language and never identify an author or Practical Sampler-controlled publisher.
  • Preserve public trust-store lifecycle handling for active, retired, revoked, and unknown recognition IDs; key rotation remains a supported metadata policy.
Implemented code: PackageOfflineRecognitionSigner.*, PackagePublisherSigning.*, PackagePublisherTrustStore.*, generated release-profile inputs, diagnostics, and lifecycle tests.
Validation evidence — 2026-08-29: the default unconfigured build and a temporary configured profile both compiled and passed drs_package_key_lifecycle_tests. The configured test exercised local Ed25519ph signing, key-ID rejection, canonical-input validation, and local audit output. The existing V3 signature mutation suite remains the wire-level tamper gate; production export/load wiring is intentionally Phase 3.

Exit gate — complete

The local signer can produce the existing V3 Ed25519ph signature entirely offline from an application-contained profile, while the public trust store remains public-only and recognition-scoped. No publisher-origin, author-identity, ownership, or post-crack forgery-resistance claim is made. Wiring this signer and trust store into every production export/load path is the next phase.

3

Connect Offline Export and Portable Loading

Implementation complete; release qualification pending

Make the built-in offline profile the normal product path so any author can export and every compatible installation can load a package without provisioning.

Development tasks

  • OPP-P3-T1 Add a production bootstrap that constructs the existing export security context from the offline key provider, local recognition signer, active IDs, and public verification store.
  • OPP-P3-T2 Install the same offline read context into standalone, plug-in, replacement, first-play, host-restore, and background sample-page paths.
  • OPP-P3-T3 Make Export Playable Instrument available to every author without an account, activation, entitlement, credential prompt, service request, or network check.
  • OPP-P3-T4 Preserve streaming record-at-a-time AEAD, bounded memory, atomic final publication, selected-record verification, cancellation cleanup, and last-known-good playback behavior.
  • OPP-P3-T5 Retain V1/V2 as bounded legacy-read-only formats and ensure no release switch, hidden command, or fallback writes them.
  • OPP-P3-T6 Remove the hosted-signer and entitlement-key prerequisites from portable-profile startup and export diagnostics while retaining fail-closed behavior for genuinely invalid profile configuration.

Validation

  • Provision a temporary non-production offline profile with a matching public recognition key, then export from a clean standalone installation and load on a second clean installation.
  • Repeat export/load through standalone, plug-in, replacement, first-play, project restore, artwork, license text, sample heads, and background page streaming using the existing injected-profile production fixture.
  • Repeat the synchronous/asynchronous export check with the generated built-in profile (the injected-profile V3 paths are covered today).
  • Verify missing/malformed profile data publishes no partial package and cannot replace last-known-good playback.
  • Run existing production-export, activation, compatibility, release-gate, and lifecycle tests under the offline production profile after key provisioning.
Implemented code: PerformancePackageOfflineSecurity.*, PerformancePackageExportService.cpp, PluginProcessor.cpp, owned offline key-source lifetime in PackageKeys.*, and production export/lifecycle tests.
Validation evidence — 2026-08-29: the Debug and Release engine lifecycle targets and V3 production-export targets compiled under the Visual Studio 2022 environment and exited successfully. The production export suite covered synchronous and asynchronous V3 export, fresh ciphertext, bounded buffers, staging cleanup, plug-in replacement, standalone loading, host restore, and fail-closed unconfigured export using its explicit fixture context. A disposable validation profile with a random 32-byte release secret, a matching Ed25519 pair, and a public trust entry was then configured in build/vs2022-debug; the positive built-in bootstrap checks, synchronous reopen, and background-preparation reopen tests passed. The clean-install UI round trip remains the final manual release gate.

Implementation gate — complete; release gate pending

The application now composes one offline profile for export and portable V3 loading. Export service startup selects the active release key, local recognition signer, and matching public verification key without accounts, services, or network access; plug-in and standalone package activation derive the same read context. Existing V3 streaming, AEAD, atomic publication, cleanup, and legacy read-only boundaries remain intact, and invalid/unconfigured profile data fails closed. Before marking this phase fully complete, provision a non-production validation profile and run the clean-install round trip plus the full release suite against it.

4

Enforce One-Way, Read-Only Packaging

Not started

Ensure package confidentiality is reinforced by product capabilities: packages play, but they do not become editable projects or ordinary sample collections.

Development tasks

  • OPP-P4-T1 Define a package-session capability policy below the UI that prohibits structural project mutation, background replacement, control-topology edits, sample replacement, mapping edits, and package rewrite.
  • OPP-P4-T2 Block package-to-project conversion, Save Project As, sample extraction/export, content-folder reveal, repacking, and authoring import for protected V3 sessions through command handlers and underlying services.
  • OPP-P4-T3 Permit exposed performance controls and host/preset state while proving they never mutate the packaged definition, artwork, routing, mappings, or encrypted records.
  • OPP-P4-T4 Keep decrypted artwork, settings, sample heads, and sample pages in bounded runtime buffers; prevent plaintext staging files and clean temporary artifacts on cancellation, failure, replacement, and shutdown.
  • OPP-P4-T5 Require the original authoring project to revise an instrument and present clear UI guidance that a changed instrument must be exported as a new package.
  • OPP-P4-T6 Audit all standalone, plug-in, host-command, keyboard, recent-file, drag/drop, and restore entry points so a package cannot reach an editable project path indirectly.

Validation

  • Attempt every prohibited action through UI commands and directly through the backing application services.
  • Attempt to replace the background, controls, mappings, routing, samples, license text, and project content; verify the operation is unavailable or rejected and the package remains byte-identical.
  • Save and restore permitted host/preset values; verify the package definition and encrypted file are unchanged.
  • Inspect export cancellation, failed activation, package replacement, teardown, and crash-recovery paths for persistent plaintext files.
  • Run the complete supported Release test suite and the established lifecycle stress workload.
Expected code: project/session capability policy, command routing, editor actions, sample and artwork services, host-state serialization, package workspace UI, teardown paths, and release-gate tests.

Exit gate

A protected V3 package is playable but cannot be opened as an editable project, converted, repacked, structurally modified, or used to extract ordinary sample files through supported Practical Sampler commands or services.

Deferred Qualification

Deferred by product decision

The phase-level tests above remain required engineering validation. The following expanded adversarial release exercise is deliberately excluded from the active implementation sequence and may be scheduled after the offline product path is complete:

  • OPP-D1-T1 Give an independent developer a production package and challenge them to replace its background while keeping it acceptable to an untouched production build.
  • OPP-D1-T2 Perform dedicated binary reverse engineering and measure the effort required to locate or reconstruct application-contained protection capability.
  • OPP-D1-T3 Attempt creation of a standalone decryptor, sample extractor, and package-forging tool after application analysis.
  • OPP-D1-T4 Obtain independent review of implementation details and public claims, then remediate release-blocking findings if this deferred phase is promoted to a release gate.
Effect of deferral: completion of OPP-0 through OPP-4 demonstrates the intended product behavior and automated integrity controls, but it does not provide a measured claim about how many hours or days a determined reverse engineer would need to crack the offline profile.

Future Licensed Instruments

Licensed instruments should be added later as a separate protection profile rather than changing the meaning of existing portable community packages.

Preserve Now

Keep versioned key IDs, wrapped content keys, recognition/signature suite identifiers, PackageKeyProvider, signing-client interfaces, and strict unknown-profile rejection.

Add Later

A licensed profile may introduce author identity, per-product or per-customer content-key delivery, activation, certificates, hosted signing, revocation, and entitlement policy.

Do Not Conflate

An offline recognition signature must never silently become evidence that a particular author is trusted or that a user owns an instrument.

Compatibility principle: future licensed readers may support both profiles, but the package identifies its profile explicitly and each profile is validated under its own trust and key-resolution policy.
