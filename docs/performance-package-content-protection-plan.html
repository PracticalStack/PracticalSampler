Engineering Initiative Plan | August 27, 2026

Performance Package Content Protection

This plan upgrades Practical Sampler playable instruments from the current deterministic custom transform to a defensible encrypted, signed, read-only distribution format. Packages remain portable and require no customer entitlement, while compiled settings, artwork, UI definitions, and sample data become resistant to direct inspection, unauthorized editing, and ordinary WAV extraction.

Decision and Security Promise

What We Protect

Compiled runtime settings, UI controls, artwork, routing, effects, sample metadata, sample heads, and sample pages are encrypted and authenticated.

What Users May Do

Users may copy a package, load it on another Practical Sampler installation, use published controls, save permitted preset state, and render audio.

What We Do Not Claim

This is not ownership enforcement or impenetrable DRM. Debugger-assisted key capture, process-memory extraction, binary patching, and audio recording remain outside the guarantee.

Defensible product statement: playable-instrument settings and samples are protected using authenticated encryption, and packages are signed to detect unauthorized modification and verify publishing origin. The design prevents direct inspection, editing, repacking, and ordinary extraction without claiming resistance to determined runtime reverse engineering.
Immutability rule: performance controls may change permitted runtime or preset values, but they never mutate the signed package definition. Background images, control topology, routing, zone definitions, and embedded content remain package-owned and read-only.

Current Technical Baseline

Area Current State Initiative Impact
Crypto provider PackageCryptoProvider is already injected into package readers, writers, and page sources. Useful seam, but requests must receive real key material or an opaque key handle.
Current algorithm PackageCrypto.cpp uses a source-visible fixed seed, FNV-style mixing, deterministic nonce generation, XOR transformation, and a forgeable custom tag. The implementation and drs.sha256.stream-seal.v1 identifier must be retired from all new exports.
Package V2 V2 already stores independently addressable, bounded metadata, sample-head, and sample-page records with AAD-like identity fields. The record/page architecture can remain; V3 changes cryptography, key envelope, signed structure, and compatibility identity.
Reader dispatch PackageReaderDispatch distinguishes DRSPKG1 and DRSPKG2. Add explicit V3 dispatch while preserving bounded legacy reads.
Runtime model Packages already omit the editable .drsproj, suppress authoring state, and activate a compiled runtime model. No authoring-format redesign is required.
Sample streaming Package-backed samples use authenticated head/page records and the common bounded cache/worker path. AEAD decryption remains off the audio thread and should preserve existing bounded memory behavior.
Release gate The current gate requires byte-identical deterministic exports. V3 must replace byte determinism with semantic determinism because secure random nonces intentionally change encrypted bytes.
Dependencies No production libsodium, OpenSSL EVP, or equivalent modern crypto integration was found outside vendored JUCE code. Dependency selection, platform linking, provenance, and update policy are first-class tasks.

Target Architecture

1. Runtime Compile Compile the editable project into runtime-only settings and bounded internal sample records. Omit original paths and WAV containers.
2. Package Key Generate a random 256-bit data-encryption key for this package and retain it only for the export operation.
3. Record AEAD Encrypt each record with XChaCha20-Poly1305 using a unique random nonce and authenticated record metadata.
4. Key Envelope Wrap the package key under a versioned Practical Sampler release key; write only the wrapped value.
5. Publish Signature Sign the header, key envelope, TOC, ordering, nonces, ciphertext, and tags with an offline publisher key.
6. Verified Open Verify signature and entitlement-free key access, then authenticate/decrypt only required records on package workers. 
DRSPKG3 cleartext envelope
  magic, formatVersion, cryptoSuite, signatureSuite
  packageId, encryptionKeyId, signingKeyId
  wrappedPackageContentKey
  bounded TOC offsets and encrypted sizes
  publisher signature

encrypted records
  runtime instrument and UI definition
  background artwork and license text
  sample metadata, heads, and bounded pages
  nonce[24] + ciphertext[n] + authenticationTag[16]

authenticated associated data
  formatVersion + packageId + recordId + recordKind
  sourceGeneration + pageIndex + plaintextSize

Key Separation

  • A unique package content key limits the effect of record/key reuse.
  • A versioned release key permits rotation without redesigning record encryption.
  • The publisher signing private key is never shipped in the application.
  • Decryption and signing keys use separate algorithms, identifiers, and operational ownership.

Plaintext Boundary

  • No plaintext record is published before tag and package-signature validation.
  • No decrypted settings, images, or samples are written to temporary files.
  • Only format dispatch and bounded range metadata remain cleartext.
  • Plaintext buffers and package keys are cleared on generation retirement where practical.

Security Contract and V3 Design

Complete Focus: decisions before implementation

Freeze the promise, attacker boundary, byte layout, key ownership, and publishing authority so implementation does not accidentally make a stronger claim than the system can support.

Development tasks
  • CPS-P0-T1 Write the content-protection ADR defining protected assets, allowed operations, excluded attacks, terminology, and exact customer-facing claim.
  • CPS-P0-T2 Specify the byte-exact DRSPKG3 header, TOC, record, AAD, key-envelope, and signature coverage contracts, including checked bounds and maximum sizes.
  • CPS-P0-T3 Decide who may sign production packages: Practical Sampler release infrastructure, a hosted author-publishing service, or provisioned author certificates.
  • CPS-P0-T4 Define release-key generation, storage, build injection, rotation, compromise response, retention, and development/test-key separation.
  • CPS-P0-T5 Define the legacy policy: V1/V2 remain readable, are labeled legacy/unprotected internally, and are upgraded only through explicit re-export.
  • CPS-P0-T6 Establish performance budgets for metadata open, head readiness, first note, page-service latency, working set, and package-size overhead.
  • CPS-P0-T7 Create a requirement-to-test traceability matrix for every confidentiality, integrity, compatibility, and real-time invariant.
Validation steps
  • Conduct product, runtime, release-engineering, and security walkthroughs of the threat model and explicit non-goals.
  • Perform paper attacks for record substitution, TOC reordering, header mutation, nonce reuse, wrong-key use, downgrade, truncation, and signing-key compromise.
  • Confirm every encrypted asset type has an owner, record kind, size bound, AAD identity, and negative test.
  • Confirm the signing workflow is possible for the actual package authors without placing a production signing key in desktop code.
Primary deliverables: security ADR, DRSPKG3 format specification, key-operations runbook, test traceability matrix, performance budget.

Exit Gate P0

Product and engineering approve the exact security promise; security approves the V3 construction and key lifecycle; signing authority has one selected implementation; every P0 decision is closed or explicitly deferred outside the release claim.

Cryptographic Foundation

Complete Focus: maintained primitives and key-aware APIs

Introduce modern, testable cryptographic primitives behind product-owned interfaces without changing the production package writer yet.

Development tasks
  • CPS-P1-T1 Select, approve, and integrate a maintained cryptographic library supporting XChaCha20-Poly1305, Ed25519, secure randomness, and secure memory utilities.
  • CPS-P1-T2 Add dependency provenance, pinned version, license review, CMake integration, supported-platform build wiring, and documented update ownership.
  • CPS-P1-T3 Replace seed-derived provider assumptions with PackageKeyProvider, key identifiers, opaque key handles, and explicit seal/open key inputs.
  • CPS-P1-T4 Implement an XChaCha20-Poly1305 provider that uses 256-bit keys, 192-bit random nonces, 128-bit tags, caller-provided AAD, and verify-before-release semantics.
  • CPS-P1-T5 Implement Ed25519 detached signature verification and signing adapters with separate public/private key types.
  • CPS-P1-T6 Add owned sensitive-buffer types with non-copying defaults and best-effort clearing on destruction and generation retirement.
  • CPS-P1-T7 Retain the deterministic legacy provider only behind V1/V2 compatibility paths and remove it as the default for new format APIs.
Validation steps
  • Run official known-answer tests or upstream vectors for AEAD and Ed25519 on every supported build architecture.
  • Prove wrong key, wrong nonce, modified ciphertext, modified tag, and modified AAD all fail without returning partial plaintext.
  • Generate at least one million test nonces through the production RNG seam and verify size, error handling, and absence of deterministic test-provider leakage into production builds.
  • Run Debug and Release builds plus focused sanitizer/static-analysis coverage where available.
  • Verify no production key bytes, test keys, environment values, or private signing material appear in compiler output, logs, diagnostics, or checked-in fixtures.
Likely files: engine_adapter/include/drs/engine/PackageCrypto.h, engine_adapter/src/PackageCrypto.cpp, new PackageKeys.*, new PackageSignature.*, CMake dependency files, focused crypto tests.

Exit Gate P1

Supported configurations build with the approved library; official vectors and all negative tests pass; production APIs cannot fall back to the fixed seed; plaintext is never returned on authentication failure; no production secret is present in source or fixtures.

Encrypted Package V3

In progress Focus: confidential runtime records and bounded paging

Build a complete V3 read/write path with per-package content keys while retaining the existing runtime-only model and page-streaming behavior.

Development tasks
  • CPS-P2-T1 Add DRSPKG3 dispatch, packed header/TOC structures, checked serialization, crypto-suite IDs, signing-key IDs, encryption-key IDs, and future-version rejection.
  • CPS-P2-T2 Generate a fresh 256-bit content key per export and a unique random 192-bit nonce per encrypted record.
  • CPS-P2-T3 Define canonical binary AAD over format version, package ID, record ID/kind, generation, page index, plaintext size, and any required compatibility identity.
  • CPS-P2-T4 Encrypt runtime settings, UI definitions, background artwork, license text, stream metadata, sample heads, and sample pages; keep only the approved envelope fields cleartext.
  • CPS-P2-T5 Ensure compilation removes source paths, original WAV names, unnecessary WAV chunks, and authoring-only metadata before encryption.
  • CPS-P2-T6 Implement bounded package-key unwrap and worker-side record decryption for metadata, heads, and requested pages without plaintext temporary files.
  • CPS-P2-T7 Update export staging, selected-record verification, cancellation, atomic publication, and cleanup to handle V3 key lifetime safely.
  • CPS-P2-T8 Replace byte-identical fixture expectations with deterministic plaintext/semantic digests and intentionally nondeterministic encrypted output.
Validation steps
  • Export identical input twice and require different nonces/ciphertexts but identical authenticated plaintext digests and rendered output.
  • Search complete package bytes for known JSON fields, control labels, source paths, filenames, PNG/JPEG signatures, RIFF/WAVE markers, and planted PCM canaries; require no plaintext matches.
  • Mutate every header/TOC/record field class and require precise rejection before the affected plaintext is published.
  • Verify package page opening reads and decrypts only the requested bounded range and leaves unrelated records unopened.
  • Audit temporary and staging directories during export/open; require no plaintext settings, image, or sample artifacts.
  • Compare V2 and V3 large-corpus metadata open, head readiness, first note, page latency, memory peak, and package-size overhead against approved budgets.
Likely files: new PackageV3.*, PackageReaderDispatch.*, PerformancePackageExportService.cpp, SampleDataSource.*, fixture tooling, package V3 tests.

Exit Gate P2

A real project exports to V3 and reopens through bounded streaming; all protected asset classes are encrypted; plaintext scanning and mutation matrices pass; no plaintext files are materialized; large-instrument performance remains within the approved budget.

3

Publisher Signatures and Release-Key Pipeline

In progress Focus: immutable origin and operational secrets

Separate confidentiality from publishing authority so extraction of a symmetric decryption key does not permit creation of a publisher-valid modified package.

Development tasks
  • CPS-P3-T1 Implement canonical signature coverage for the complete header, wrapped content key, TOC, record ordering, nonces, ciphertext, and authentication tags.
  • CPS-P3-T2 Add a pinned public-key trust store with signing-key identifiers, activation/revocation metadata, rotation rules, and unknown-key rejection.
  • CPS-P3-T3 Build the selected publishing workflow so the Ed25519 private key exists only in controlled release/signing infrastructure or approved author hardware/credentials.
  • CPS-P3-T4 Build release-key generation and injection/provisioning without checking secrets into source, fixtures, build logs, symbols, crash reports, or distributable debugging artifacts.
  • CPS-P3-T5 Wrap each package content key under the active release key and support explicit lookup by key ID, rotation, and controlled legacy-key retention.
  • CPS-P3-T6 Verify the publisher signature before accepting package-owned settings, artwork, controls, or sample records into an activation generation.
  • CPS-P3-T7 Add operational runbooks for signing outage, key rotation, suspected compromise, package revocation policy, and emergency reader update.
Validation steps
  • Use a deliberately disclosed test decryption key to create AEAD-valid modified content and prove publisher-signature verification still rejects it.
  • Test altered signature, wrong signing key, unknown key ID, revoked test key, key-ID substitution, record reordering, cross-package record substitution, and signature truncation.
  • Inspect source, repository history, produced packages, CI logs, application logs, crash artifacts, symbols, and test fixtures for private signing or release-key leakage.
  • Exercise a complete signing-key rotation and verify new packages open, retained-key packages follow policy, and unknown/retired keys fail with actionable diagnostics.
  • Run the real package-author workflow end to end and confirm production signing cannot be invoked by an unauthorized desktop build.
Likely files: PackageSignature.*, PackageKeys.*, V3 reader/writer, release tooling, CI secret configuration, publishing service or author-certificate tooling, operational documentation.

Exit Gate P3

No production signing private key exists in shipped code; an attacker holding the symmetric test decryption key still cannot create an accepted modified package; key rotation and failure recovery are demonstrated; the authorized publishing workflow is operational and auditable.

Product Cutover and Compatibility

In progress Focus: safe adoption without breaking existing packages

Make V3 the only new export format, preserve deliberate legacy reads, and integrate secure failure behavior across standalone, plugin, host restore, and support surfaces.

Development tasks
  • CPS-P4-T1 Switch Export Playable Instrument to V3 and remove the deterministic provider from every default production writer path.
  • CPS-P4-T2 Preserve read-only V1/V2 dispatch with explicit internal legacy security classification, size bounds, and no rewrite-on-open behavior.
  • CPS-P4-T3 Add explicit re-export guidance for creators who need to migrate existing packages; never imply that an old file was secured in place.
  • CPS-P4-T4 Add distinct diagnostics for unsupported format, unknown key, unavailable key, bad signature, AEAD failure, corruption, compatibility mismatch, cancellation, and I/O failure.
  • CPS-P4-T5 Integrate V3 with deferred activation, package replacement, last-known-good playback, host state restore, plugin/standalone open flows, and package license/artwork viewing.
  • CPS-P4-T6 Update support, operator, compatibility, and customer-facing documentation with the approved promise and explicit non-goals.
  • CPS-P4-T7 Add telemetry that reports only non-sensitive suite/key identifiers and failure categories; prohibit keys, plaintext, nonces, tags, and protected metadata from logs.
Validation steps
  • Run the complete checked-in V1/V2 positive and negative corpus unchanged and verify no legacy file is rewritten.
  • Export/reopen V3 through standalone, plugin, host restore, package replacement, and first-play paths.
  • Attempt failed V3 replacement while a valid package is active and prove last-known-good playback remains active without publishing failed plaintext.
  • Verify UI and logs distinguish security failures without leaking internal paths, keys, encrypted content, or attacker-controlled unbounded strings.
  • Confirm all normal production export entry points emit V3 and no hidden/test switch can emit the legacy format in release builds.
Likely files: PackageReaderDispatch.*, PluginProcessor.cpp, standalone open flow, ProjectRestoreCoordinator.cpp, PerformancePackageExportService.cpp, diagnostics, compatibility/operator docs.

Exit Gate P4

Every production export is signed V3; standalone, plugin, replacement, and restore paths open it correctly; V1/V2 remain bounded legacy-read only; failure diagnostics are actionable and non-sensitive; migration documentation is complete.

Adversarial Hardening and Release Qualification

Blocked Focus: evidence, performance, and independent review

Qualify the implementation as a long-lived hostile-input boundary and produce reproducible evidence for the exact content-protection promise.

Development tasks
  • CPS-P5-T1 Build checked-in V3 positive/negative fixtures and mutation generators covering every header, TOC, envelope, signature, nonce, tag, ciphertext, and bounds field class.
  • CPS-P5-T2 Add coverage-guided fuzz targets for format dispatch, header/TOC parsing, key-envelope parsing, signature verification, record framing, and AAD construction.
  • CPS-P5-T3 Extend the Accurate Salamander qualification with V3 export throughput, package size, metadata open, head readiness, page latency, first note, cache peak, cancellation, and sustained playback evidence.
  • CPS-P5-T4 Add automated plaintext-leak scans over packages, staging directories, temp directories, logs, crash artifacts, and host state.
  • CPS-P5-T5 Update the package release gate to require semantic determinism, signature validity, mutation rejection, confidentiality scans, shell parity, legacy compatibility, and real-time safety.
  • CPS-P5-T6 Conduct focused manual reverse-engineering review at the declared threat boundary, including archive/hex inspection, record carving, key-string scans, and attempted package repacking.
  • CPS-P5-T7 Obtain independent cryptographic/security review of construction, key operations, implementation, test coverage, and public claims; remediate all release-blocking findings.
  • CPS-P5-T8 Freeze V3 compatibility policy, incident owner, dependency-update cadence, release checklist, and support escalation path.
Validation steps
  • Run fuzzers for the agreed execution budget with zero crash, out-of-bounds, unbounded allocation, or unauthenticated plaintext findings.
  • Run focused tests, full repository tests, standalone/plugin host validation, and Release large-corpus qualification.
  • Compare all performance measures with frozen V2 and authored-project baselines; investigate every budget regression rather than raising thresholds without review.
  • Prove no protected plaintext appears in package bytes or persistent artifacts and no decryption/signature/file operation executes on the audio thread.
  • Have an independent reviewer reproduce wrong-key, compromised-symmetric-key, mutation, downgrade, and extraction-resistance evidence from documented commands.
Primary deliverables: V3 corpus, fuzz harnesses, large-instrument report, content-protection release-gate JSON, independent review report, frozen compatibility and incident runbooks.

Exit Gate P5 / Release Gate

All automated gates are green; performance budgets pass; no unresolved critical/high security findings remain; independent review supports the approved claim; release, rotation, incident, migration, and support procedures are signed off by their owners.

Cross-Phase Validation and Release Gates

Mandatory Security Gates

  • Approved maintained cryptographic library; no custom cipher or tag construction.
  • Unique random per-record nonces and random per-package content keys.
  • No source-visible production secret or shipped signing private key.
  • Publisher signature covers all mutable package structure and encrypted content.
  • Wrong-key, bad-signature, mutation, substitution, downgrade, and truncation rejection.
  • No plaintext settings, artwork, filenames, WAV containers, or planted PCM in package bytes.
  • No unauthenticated plaintext publication or plaintext temporary files.

Mandatory Product Gates

  • V3 package opens in standalone, plugin, and host restore paths.
  • Package remains read-only and authoring state remains absent.
  • Published controls and preset overrides retain intended behavior.
  • V1/V2 continue to open under the bounded compatibility policy.
  • Large-instrument load, memory, and page-service budgets pass.
  • Support diagnostics are specific without exposing protected data.
Release blocker: do not ship V3 if production signing authority is present in the desktop binary, if identical exports reuse nonces, if authenticated plaintext is exposed before verification, if original WAV containers remain directly recoverable from package bytes, or if any production path silently falls back to the deterministic provider.

Risks and Required Decisions

Risk / Decision Impact Mitigation or Required Decision Owner Gate
Signing authority If arbitrary desktop exporters possess the publisher private key, package-origin verification is not defensible. Select controlled vendor signing, hosted author publishing, or an author certificate chain during Phase 0. P0
Shared decryption key A determined reverse engineer can eventually extract an offline shared key. Use per-package content keys, versioned wrapping keys, signature separation, rotation, and claims limited to direct inspection/extraction deterrence. P0/P3
Key loss or compromise Lost keys can strand packages; compromised keys weaken confidentiality or publishing trust. Document backup, escrow, access control, rotation, retained-reader policy, revocation semantics, and incident response. P3
Third-party dependency Build portability, supply chain, licensing, and security updates become release responsibilities. Pin provenance, automate platform builds/tests, monitor advisories, and assign an update owner. P1
Performance regression Record verification may increase worker CPU, first-note latency, or page-miss recovery time. Benchmark from Phase 2 onward; preserve bounded pages and keep all cryptographic work off the audio thread. P2/P5
Compatibility ambiguity Legacy packages cannot be retroactively secured and silent rewrites risk data loss. Read V1/V2 under explicit legacy policy; write only V3; migrate only through verified re-export. P4
Overstated marketing Claims such as “impossible to extract” exceed what an offline audio client can guarantee. Use the approved statement from this plan and require security review for changes to customer-facing language. P0/P5
