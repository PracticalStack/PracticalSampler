Playable Instrument Package Plan

This plan defines a second DRS output artifact: a sealed, playable instrument package that opens inside DRS in a Performance-only workspace. The package excludes the authored .drsproj, carries only runtime-facing content, and encrypts its internal assets so extraction and authoring-side mutation become intentionally inconvenient without claiming strong copy protection.

Goal and Product Frame

What We Are Building

A DRS-native package that opens as a playable instrument, not as an authored project. It uses the existing runtime engine and performance surface, but hides the authoring surface entirely.

What It Protects Against

Casual browsing of raw sample files, trivial manifest editing, and accidental re-entry into the authoring workflow.

What It Does Not Promise

It is not DRM and does not claim to stop a determined reverse engineer who can instrument a running copy of DRS.

Core product decision: the playable package is a distinct document type, not a disguised drs.project. The runtime instrument becomes authoritative, and authoring content is absent from the package.
Naming decision: this plan uses .drpkg as the package extension and drs.performancePackage as the top-level schema name. If branding wants a different extension later, keep the schema split intact.

Current Codebase Baseline

Area Current State Implication
Runtime models RuntimeProjectModel and RuntimeInstrumentModel are already separated in engine_adapter/include/drs/engine/RuntimeModel.h. Good foundation for removing authoring data from the playable package.
Compiler seam compileRuntimeInstrument(...) exists in engine_adapter/src/RuntimeCompiler.cpp. We can build from an authored project into runtime artifacts, but the app does not yet expose a complete package writer.
Project save flow saveProjectFiles(...) writes plain .drsproj and .drinst files in app/src/shared/ProjectStorage.cpp. Current save logic is not suitable for sealed distribution output.
Workspace shell Standalone and plugin editors always add both Perform and Map tabs. We need a document/workspace mode that can suppress the authoring tab entirely.
Fixture packaging The repo already generates a reference drs.referencePackage manifest for fixtures. There is a useful packaging vocabulary, but not yet a customer-facing sealed container.
Crypto baseline JUCE crypto modules are vendored, but the obvious HISE BlowFish utilities are obfuscation-oriented and not the right long-term package primitive. We should define a product-owned AEAD provider abstraction and avoid tying this feature to weak legacy helpers.

Target Artifact Model

Authoring Output

  • .drsproj remains the editable source of truth.
  • .drinst remains a plain runtime manifest for internal development, tests, and fixture review.
  • Authoring workflows continue to target the current workspace shell.

Distribution Output

  • .drpkg becomes the customer-facing playable instrument package.
  • The package contains runtime-only content: package manifest, instrument manifest, compiled stream index/data, presets, artwork, and package metadata.
  • The package does not contain .drsproj or any authoring-state graph.
Authority rule: when a .drpkg file is opened, all runtime behavior must be driven from package payloads alone. No hidden fallback to a nearby .drsproj, sibling sample folder, or project-derived editable model is allowed.
1. Authored Project Editable source model with full authoring graph and sample references.
2. Runtime Compile Compile project data into a runtime instrument plus stream mapping and payload plan.
3. Stream Build Produce the package-owned sample payload and index with deterministic offsets and checksums.
4. Package Manifest Assemble metadata, compatibility bounds, payload map, and visible document summary.
5. Encrypt and Seal Compress, encrypt, authenticate, and write the final .drpkg container.
6. Performance Open Load through a package reader and enter Performance-only workspace mode.

Package Format and Crypto

Recommended Container Shape

  • Cleartext fixed header with magic, version, package id, display name, payload table offset, flags, and minimum compatible app version.
  • Encrypted table-of-contents describing each logical payload.
  • Encrypted payload blobs for instrument manifest, compiled stream index, compiled sample pages, presets, artwork, and optional notes.
  • Per-payload checksums and sizes recorded inside the authenticated metadata.

Crypto Recommendation

  • Use authenticated encryption, not plain symmetric obfuscation.
  • Prefer a product-owned AEAD abstraction whose first concrete provider is a vendored modern primitive such as XChaCha20-Poly1305 or AES-256-GCM.
  • Avoid relying on legacy HISE BlowFish helpers for this format.
  • Compress first, then encrypt, so repetitive sample metadata is not leaked.
cleartext header
  magic = "DRSPKG01"
  packageSchema = 1
  minReaderVersion
  packageId
  displayName
  tocOffset
  tocSize
  headerFlags
  visibleThumbnailOffset? / visibleThumbnailSize?

encrypted TOC
  packageManifest.json
  instrumentManifest.json
  compiledStream.index
  compiledStream.pages
  defaultPreset.json
  artwork/*
  diagnostics/build-info.json
Important technical gap: the current compiler emits stream metadata and manifest serialization, but not yet a final sealed package with a production binary sample payload format. The stream writer must become a first-class product seam, not a test-only descriptor.

Open and Export Flows

Export Flow

  1. User selects Export Playable Instrument from a project.
  2. DRS validates the project for distribution eligibility.
  3. Compiler builds runtime instrument and stream payload.
  4. Packager assembles, encrypts, and writes .drpkg.
  5. Validation pass reopens the written package and confirms performance playback readiness.

Open Flow

  1. User opens a .drpkg file.
  2. Reader validates header, version, and authentication tag.
  3. Package loader hydrates runtime instrument and stream services from package payloads.
  4. Workspace enters performanceOnly mode.
  5. Only the Perform surface is shown; authoring actions are absent.

1

Package Contract and Workspace Mode

Focus: schemas, document identity, shell mode

Define the contract before touching encryption or export UI so every later sprint has a stable vocabulary.

  • PKG-S1-T1 Create an ADR and code contract for drs.performancePackage, .drpkg, compatibility versioning, and package non-goals.
  • PKG-S1-T2 Introduce a document-kind/workspace-mode enum that differentiates editable projects from performance packages.
  • PKG-S1-T3 Add shell plumbing so standalone and plugin editors can suppress the Map tab when opening a performance package.
  • PKG-S1-T4 Define package manifest structs and serialization contracts in engine_adapter/include/drs/engine.
  • PKG-S1-T5 Add contract tests that assert authoring components are unavailable in performanceOnly mode.
Likely files: MainComponent.cpp, PluginEditor.cpp, new PackageModel.h, new docs contract.

Exit Criteria

The codebase can represent a performance package as a first-class document type and can render a shell that exposes only the Perform view.

2

Compiler Finalization and Stream Writer

Focus: deterministic runtime payload generation

Turn the current compile seam into a real packageable runtime output instead of a mostly manifest-oriented fixture path.

  • PKG-S2-T1 Split compile output into explicit logical artifacts: instrument manifest, stream index, binary sample payload pages, optional preset bundle.
  • PKG-S2-T2 Replace or extend the prototype stream container serializer with a production binary writer plus deterministic index format.
  • PKG-S2-T3 Add checksums, page accounting, and payload-size metrics that are stable across repeated compiles.
  • PKG-S2-T4 Add reference fixture tests for binary stream output determinism and round-trip loader readability.
  • PKG-S2-T5 Add negative tests for missing samples, duplicate source ids, unsupported sample metadata, and invalid payload offsets.
Likely files: RuntimeCompiler.cpp, new CompiledStreamWriter.*, compile-path tests, fixture tooling.

Exit Criteria

A project can be compiled into complete runtime-owned payloads without depending on the plain project save flow.

3

Package Crypto and Sealed Writer

Focus: authenticated package format

Build the encryption boundary as a product-owned seam instead of sprinkling ad hoc crypto into the exporter.

  • PKG-S3-T1 Introduce a PackageCryptoProvider abstraction with test vectors and deterministic harness coverage.
  • PKG-S3-T2 Implement the package header, encrypted TOC, payload records, nonce handling, and authentication-tag validation rules.
  • PKG-S3-T3 Define the cleartext-vs-encrypted metadata boundary, including visible display name and optional thumbnail policy.
  • PKG-S3-T4 Write a PackageWriter that consumes compiled runtime artifacts and emits a single .drpkg file.
  • PKG-S3-T5 Add corruption tests for truncated files, bad tags, duplicate payload ids, TOC mismatch, and version skew.
Likely files: new PackageCrypto*, PackageWriter*, new package-format tests.

Exit Criteria

The repo can write a sealed, authenticated package from compiled runtime artifacts and reliably reject tampered packages.

4

Package Reader and Runtime Loader

Focus: loading .drpkg without authoring fallback

Make the sealed package loadable through a dedicated reader path that hydrates runtime state directly.

  • PKG-S4-T1 Add a PackageReader that validates the cleartext header, decrypts the TOC, and streams payloads on demand.
  • PKG-S4-T2 Add loadPerformancePackage(...) entry points beside the existing project and instrument loaders.
  • PKG-S4-T3 Teach the runtime loader to hydrate instrument and stream services from package-owned payloads instead of file-neighbor assumptions.
  • PKG-S4-T4 Ensure no package-open path constructs a RuntimeProjectModel or editable authoring session.
  • PKG-S4-T5 Add unit tests for successful open, checksum mismatch, unsupported version, missing required payload, and wrong package schema.
Likely files: RuntimeLoader.*, new PackageReader*, new package-load tests.

Exit Criteria

A .drpkg file can be opened into a playable runtime session without requiring a project manifest or a raw sample directory.

7

Hardening, Negative Fixtures, and Host Validation

Focus: resilience and supportability

Treat packaging as a long-lived product surface with bad-input handling, diagnostics, and reproducible fixtures.

  • PKG-S7-T1 Add checked-in positive and negative package fixtures: valid, truncated, tampered, wrong-version, missing-payload, and checksum-mismatch.
  • PKG-S7-T2 Add runtime diagnostics that distinguish package-format failure, decryption failure, payload corruption, and playback-compatibility failure.
  • PKG-S7-T3 Extend REAPER or host validation scenarios so a sealed package can be opened and played in plugin and standalone paths.
  • PKG-S7-T4 Add performance and memory profiling around package open, stream paging, and initial playback latency.
  • PKG-S7-T5 Add docs for contributor fixture refresh, package verification, and debug triage.
Likely files: validation/reaper/*, tests/src/*, package docs, fixture tool extensions.

Exit Criteria

The package system is supportable under corruption, version skew, and host-level playback validation.

8

Release Gate and Cutover

Focus: production readiness

Ship only after packaging is deterministic, debuggable, and clearly separated from the editable project flow.

  • PKG-S8-T1 Freeze the package schema and compatibility policy, including reader behavior for future minor and major versions.
  • PKG-S8-T2 Add go/no-go evidence for package determinism, reopen validation, performance-only UX, and failure reporting.
  • PKG-S8-T3 Audit menus, commands, and docs to ensure Save Project and Export Playable Instrument remain clearly distinct.
  • PKG-S8-T4 Add release checklist items for customer package corpus smoke tests and package-format regression tests.
  • PKG-S8-T5 Publish operator docs for support and internal QA.
Likely files: release docs, test presets, gate reports, operator notes.

Exit Criteria

The playable package feature is ready to ship as a distinct output with clear user expectations and stable reader/writer behavior.

Validation and Release Gates

Must-Have Gates

  • Deterministic package generation from identical inputs.
  • Successful reopen of exported package in standalone and plugin shells.
  • No authoring tab, authoring save prompts, or editable project state in package sessions.
  • Negative fixture coverage for corruption and version mismatch.
  • Host validation proving package-backed playback through the runtime engine.

Should-Have Gates

  • Package open-time and first-note latency budgets.
  • Contributor tooling to rebuild and verify package fixtures.
  • Human-readable diagnostics for common field failures.
  • Compatibility tests across at least one previous reader format revision once the schema evolves.
Release blocker: do not ship the format if the runtime can still silently fall back to nearby raw sample files or project manifests. That would undercut both the packaging goal and the support model.
