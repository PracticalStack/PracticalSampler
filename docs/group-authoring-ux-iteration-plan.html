Next Iteration 2 | Group authoring

Make Groups Inspectable and Manageable

Improve the Practical Sampler group workflow before adding more layer-aware authoring. A creator should be able to identify every group by a clear name and stable ID, understand its membership at a glance, select all of its zones, rename and reorder it, move zones between groups, and see group membership directly in the Map.

01 | Product frame

Goal and scope

Creator outcome

The Groups workbench answers three questions without opening individual zones: What is this group called? Which zones belong to it? Where is it in the processing and authoring order?

Engineering outcome

Group operations become explicit transactions over the existing native model. Membership remains derived from each zone’s groupId; the UI does not maintain a second, competing membership list.

Explicit non-goals

This iteration does not add layer assignment workflows, layer crossfade behavior, macros, new group DSP, or a new persistence schema. It prepares the group surface that those features will consume.

Scope boundary

All implementation, tests, fixtures, and this plan belong to PracticalSampler/. The sibling _analysis/Rhapsody/ tree is excluded. Existing HTML documentation is not rewritten; this file is the new planning artifact. Update active Markdown only when the authoring contract changes.

02 | Ground truth

Current baseline to extend

Practical Sampler already persists authored groups with an ID, display name, display order, visibility, gain, pan, routing, and audition anchor. Zones carry the authoritative groupId. AuthoringSession already exposes group selection, creation, deletion, reorder, and zone reassignment transactions, while AuthoringPanel already has a Groups workbench and a Map selection bridge.

Zone modelEach zone stores its parent groupId.
Group modelIdentity and display order are persisted independently from zones.
Authoring sessionMutations are transaction-backed and support undo/redo.
Groups workbenchShows group rows and selected-group controls, but needs stronger inspection and membership actions.
MapAlready supports zone selection; this iteration adds persistent group context.

Primary UX gap

Group rows need to make name, stable ID, zone count, visibility, and selection state legible at the same time. “Selected group” must be a meaningful authoring context, not merely an index in a list.

Primary model guardrail

Renaming changes displayName only. The stable id remains unchanged so routing sources, layer references, undo history, fixtures, and external project identity do not break.

Reference seams: RuntimeModel.h, AuthoringSession.h, AuthoringSession.cpp, AuthoringPanel.h, and AuthoringPanel.cpp.

03 | Locked contract

Group identity, membership, and operations

Identity:
group.id = stable project identity
group.displayName = user-facing editable label

Membership:
zone.groupId = authoritative parent relationship
group.zoneCount = derived count of zones where zone.groupId == group.id

Selection:
select group → selectedGroupId + optional selected zone set
select all zones in group → replace Map selection with that group’s member zones

Empty groups are valid

Do not silently delete a group when its last zone moves away. Empty groups remain inspectable and reorderable until the existing explicit Delete Group action is used. Deleting a group must use an explicit, documented policy for its zones; the preferred safe behavior is to require reassignment or offer a destination-group choice before commit.

04 | Execution plan

Development tasklist

0

Baseline and interaction contract

Lock behavior before UI expansion

Capture the current group seams and define the exact selection, identity, ordering, and membership behavior that the workbench and Map must share.

  • GUX0.1 Inventory current group persistence, transaction helpers, selection state, Map selection synchronization, and existing group-related tests.
  • GUX0.2 Define the group row/read-model fields: display name, stable ID, derived zone count, visibility, display order, selected state, and empty-group state.
  • GUX0.3 Define the selection contract for “Select Group” versus “Select All Zones”: selecting a row selects the authoring group; the explicit action replaces the Map zone selection with all members.
  • GUX0.4 Define validation and transaction rules for blank names, duplicate IDs in imported/malformed content, empty groups, group deletion, and reorder boundaries.
  • GUX0.5 Add fixture cases covering named groups, stable IDs, an empty group, two groups with movable zones, and zones spread across the Map.

Gate 0

The contract is written in tests or fixture assertions, and no behavior depends on a stored zone count or a mutable group ID.

1

Inspectable group read model

Make the hierarchy legible

Give every group consumer one consistent summary so the Groups workbench, selection summary, accessibility text, and Map legend cannot disagree.

  • GUX1.1 Add or strengthen an AuthoringGroupSummary view model containing stable ID, display name, display order, zone count, visibility, selected state, and empty-state metadata.
  • GUX1.2 Centralize derived member collection and zone counting so every caller uses the same group membership definition.
  • GUX1.3 Update the Groups list rows to show name as the primary label, ID as secondary metadata, and “N zones” as a persistent count.
  • GUX1.4 Add accessible names/descriptions and keyboard focus order for group rows, group actions, and empty groups.
  • GUX1.5 Ensure selection and refresh preserve the selected group by ID rather than by stale list index.

Gate 1

A user can identify every group and its membership size without opening a zone editor, and the same values survive save/reload.

2

Group management actions

Rename, reorder, and move membership

Turn the existing group transactions into a coherent authoring workflow with clear feedback, predictable selection, and safe membership changes.

  • GUX2.1 Implement stable group rename editing with trim/blank validation, transaction labels, undo/redo, dirty-state updates, and immediate list/inspector refresh.
  • GUX2.2 Add group reorder controls that normalize display order, preserve group identity, and retain selection on the moved group.
  • GUX2.3 Add “Select All Zones” to the selected-group controls and make it operate through the existing Map selection bridge.
  • GUX2.4 Add a destination-group action for selected zones, including no-selection, no-destination, and mixed-source-group feedback.
  • GUX2.5 Reconcile audition anchors when zones move; if an anchor leaves its group, select a deterministic remaining member or clear the anchor.
  • GUX2.6 Re-run group-scoped Round Robin validation/reconciliation after membership changes and surface any resulting status in the group inspector.
  • GUX2.7 Define the explicit Delete Group behavior for non-empty groups and ensure accidental deletion cannot orphan zones.

Gate 2

Rename, reorder, select-all, and zone reassignment are undoable, persist correctly, and leave no zone with an invalid group reference.

3

Map group membership presentation

Make membership visible where zones are edited

Expose group membership directly in the Map without replacing the existing zone-range visualization or making color the only source of truth.

  • GUX3.1 Add a deterministic group color/visual token derived from group identity or display order, with sufficient contrast and a non-color fallback.
  • GUX3.2 Render group membership in Map zones through an outline, badge, lane tint, or label treatment that remains legible for overlapping ranges.
  • GUX3.3 Add a group legend or filter showing group name, ID, zone count, and visibility state; selecting a legend entry selects the group context.
  • GUX3.4 Make Map selection and Groups selection synchronize in both directions without clearing unrelated selection state unexpectedly.
  • GUX3.5 Refresh visual membership after rename, reorder, move, import materialization, undo, redo, and project reload.
  • GUX3.6 Add tooltips/accessibility text that state the group name, stable ID, and zone membership for each Map item.

Gate 3

While editing the Map, a user can tell which group each visible zone belongs to and can move from a visual member to the corresponding group controls.

4

Tests, documentation, and release hygiene

Prove the contract end to end

Protect the group contract across persistence, authoring transactions, Map view models, and application builds before the layer-assignment iteration begins.

  • GUX4.1 Add contract tests for stable IDs, rename persistence, derived zone counts, empty groups, display-order normalization, and invalid membership references.
  • GUX4.2 Add authoring transaction tests for select-all, move selected zones, multi-zone reassignment, undo/redo, anchor repair, deletion safety, and selection retention.
  • GUX4.3 Add Map view-model/render tests for group visual tokens, legend contents, group/zone selection synchronization, and refresh after edits.
  • GUX4.4 Add regression coverage for import-created default groups and for existing group-scoped Round Robin and routing behavior.
  • GUX4.5 Update active Markdown policy or authoring guidance to describe stable group IDs, derived counts, and the group-before-layer workflow. Do not retrofit old HTML documentation.
  • GUX4.6 Run the focused group test matrix, plugin and standalone builds, git diff --check, and clean-checkout verification for tracked-path and fixture completeness.

Gate 4

The focused group matrix passes, both application targets build, and the next layer-assignment iteration can rely on groups as inspectable, stable containers.

06 | Guardrails

Risks and decisions

Selection ambiguity

“Select group” and “select all zones” are related but different actions. Keep the group context selected independently from the Map’s zone selection and label the all-zone action explicitly.

Identity breakage

Never use a display name as a foreign key. Group IDs are stable and remain unchanged by rename, reorder, layer assignment, routing, or Map color changes.

Visual overload

Group membership must supplement key-range, velocity-range, and selection visuals. Use labels, outlines, or patterns so users do not depend on color alone.

Cross-feature coupling

Moving zones can affect audition anchors and Round Robin validity. Route the operation through one transaction boundary and refresh all derived summaries afterward.

Implementation order

Build the shared summary and transaction contract first, then add the workbench actions, then add Map presentation. This keeps the Map as a consumer of authoritative membership rather than a second place where grouping rules are implemented.

07 | Completion criteria

Release gate

Iteration 2 is complete when

  • Every group row exposes a clear name, stable ID, and derived zone count.
  • Users can select all zones in a group, rename groups, reorder groups, and move selected zones between groups.
  • Group IDs remain stable and all mutations are undoable, persisted, and validated.
  • The Map visibly communicates membership and synchronizes group and zone selection.
  • Existing group, layer, routing, Round Robin, import, and runtime behavior remains green.
  • Focused tests, plugin/standalone builds, clean-checkout checks, and release hygiene checks pass.

Planned implementation surfaces include AuthoringSession.h, AuthoringSession.cpp, AuthoringPanel.h, AuthoringPanel.cpp, and the existing ZoneMapCanvas.h / Map view-model seams.
