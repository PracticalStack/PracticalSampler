Recommendation

Ship V1 as a capable native sampler—with a named compatibility boundary.

The implementation is already substantial enough for a meaningful V1. The release should not imply “complete SFZ” or “complete synthesis.” It should promise a reliable, non-destructive instrument-building and playback core, then make SFZ fidelity and DSP depth the first two roadmap tracks.

V1 positioning

Practical Sampler V1 imports WAV, FLAC, and a documented subset of SFZ into a native project; lets creators map, layer, articulate, modulate, and loop sample instruments; auditions changes through the same sampler core used for performance; and publishes streamable playable packages for standalone and VST3 use.

Become the most practical open sampler for turning real-world libraries into durable, editable instruments—without making scripts the answer to missing fundamentals.

V1 capability statement

What is implemented now.

“Implemented” below means there is a product-owned runtime path and corresponding test or release-evidence surface in the repository. Some items are deliberately bounded; those boundaries are called out in the next section.

Implemented

Native sampler playback core

  • Shared immutable render model for Preview and Performance, with isolated voice and event state.
  • Sample-rate conversion through pitched playback, voice allocation/stealing, gated and one-shot voices, and deterministic event ordering.
  • Mono/stereo sample rendering, per-zone gain, pan, tuning, velocity response, and bounded real-time diagnostics.
  • Key and velocity mapping, overlapping velocity crossfades, sequential and supported equal-probability random round robins.
Implemented

Regions, looping, and envelopes

  • Non-destructive sample start/end, loop start/end, no-loop, one-shot, continuous-loop, and sustain-loop behavior.
  • WAV loop-metadata fallback and native equal-power loop crossfade.
  • Hold, decay, sustain, release time and release shape; velocity tracking; controller-driven hold/decay/sustain.
  • Release-trigger routes and duration-independent release sample playback.
Implemented

Performance and articulation engine

  • First-class articulation identities with a default articulation and consumed latch-note activation.
  • Semantic note-on, note-off, effective release, pedal-down, pedal-up, and controller-change events.
  • Per-articulation routes, release/pedal noises, exclusive groups, choke targets, and configurable choke release.
  • Round-robin resets, attack-context retention, deterministic pedal ordering, and state continuity across published generations.
Implemented

Pedals, controls, and modulation

  • Binary sustain plus continuous CC64 half-pedal release curves, repedal behavior, and per-route damper metadata.
  • Instrument Controls with stable MIDI CC binding, defaults, channel scope, and many-to-many target projection.
  • Live or note-on control of gain, pan, tuning, envelope hold, decay, and sustain.
  • Imported 128-point SFZ curves for supported tuning, amplitude, envelope, and damper paths.
Supported profile

WAV, FLAC, and SFZ intake

  • WAV and FLAC source intake for mono/stereo assets; RIFF/RF64 WAV streaming for PCM16/24/32 and float32.
  • One-way SFZ parsing with #include/#define handling, inheritance, path normalization, cancellation, and hostile-input budgets.
  • Analyze-first compatibility reporting: converted, approximated, report-only, or blocking—never silent parity claims.
  • Projection of common mapping, gain, pan, tuning, CC conditions, crossfade, round-robin, loop, trigger, and envelope opcodes.
Implemented

Native authoring data model

  • Versioned project model for sample sources, zones, groups, layers, articulations, macros, controls, DSP slots, buses, and performance rules.
  • Layer → group → zone hierarchy with independent gain/pan/routing stages and velocity- or controller-driven layer crossfade.
  • Transactional non-destructive edits, migration, validation, Preview preparation, and explicit Publish activation.
  • Stable IDs and deterministic compilation from editable authoring data to immutable callback-ready structures.
Implemented

DSP graph and macro binding

  • Ordered DSP graph at zone, group, layer, and instrument scope with versioned algorithms and parameter validation.
  • Gain, saturator, stereo delay, algorithmic reverb, compact EQ, and chorus.
  • Parameter smoothing, musical control laws, macro-to-DSP mapping, bypass, unavailable-effect preservation, and graph budget checks.
  • Immutable graph generation and safe block-boundary replacement reuse the sampler’s real-time architecture.
Implemented

Large instruments and distribution

  • Bounded resident heads, page cache, lock-free page intents, underrun recovery, and deferred activation for large instruments.
  • Authenticated 64-bit package-v2 records with independently readable metadata, heads, and pages.
  • Editable .drsproj projects and sealed read-only .drpkg playable instruments.
  • Project reopen, missing-media recovery, VST3 host-state recall, and old-generation lifetime protection.
V1 boundary

What V1 should say plainly.

These are not reasons to delay V1. They are the most important product promises not to make yet, and they explain the order of the roadmap.

BoundaryCurrent realityUser impact
SFZ is a conversion profile The parser recognizes arbitrary opcodes, but only a documented subset receives native behavior. Unknown or unsupported semantics remain report-only. There is no SFZ export. Some libraries import structurally but do not sound identical. The compatibility report is part of the workflow, not an edge case.
Keyswitch import is incomplete Native consumed latch-note articulations work, but SFZ sw_* selection opcodes remain report-only rather than materializing articulation rules. Multi-articulation SFZ libraries often require manual reconstruction.
Articulation activation is narrow Activation is one consumed note-on latch rule per articulation. Momentary switches, CC/program activation, composite conditions, and transition rules are not part of the current contract. Complex orchestral and performance libraries cannot express their full switching model natively yet.
Voice DSP is partial The amplitude envelope has hold/decay/sustain/release but no authored attack stage. There is no per-voice filter, filter/pitch envelope, LFO, general modulation matrix, glide, or legato engine. V1 is strong at faithful sample mapping but limited at deep sound design.
DSP algorithms are foundational The graph, versioning, control laws, and real-time activation are good; the six algorithms are intentionally compact and the parameter surface is catalog-specific. The pipeline is production-minded, but the sonic palette and authoring vocabulary feel basic.
MIDI expression is limited Notes, CCs, sustain, and exact-channel control bindings work. Core route selection remains omni; pitch bend, pressure, per-note expression, program change, and MPE are not native modulation sources. Expressive controllers cannot yet drive the sampler comprehensively.
Package parity has exclusions The current package projection rejects authored performance banks and non-default group/zone pan instead of silently losing them. Those projects must be simplified or the parity gap must be closed before export.
Output and source topology is simple The plug-in exposes one stereo output and the renderer accepts mono/stereo sources. There is no multi-output kit routing or native multichannel sample topology. Drum, mic-position, surround, and stem workflows have a practical ceiling.
What else is needed

Six systems—not a longer feature list.

The next leap is to turn today’s strong vertical slices into reusable engine systems. That reduces the “new instrument, new blocker” pattern and gives scripting a stable platform later.

1 · Compatibility

A named Practical SFZ Profile

Define support by audible behavior, scope, and value—not merely parser recognition. Maintain a corpus matrix, opcode families, reference renders, and a promotion rule from report-only to native.

2 · Articulations

A composable performance rule model

Make articulations own activation, eligibility, transitions, fallback, release behavior, and controller state. SFZ keyswitches then become an import adapter to this model.

3 · Modulation

One source-to-target modulation graph

Unify velocity, key, CC, bend, pressure, envelopes, LFOs, random, macros, and transport. Define note-on versus live-rate evaluation and smoothing once.

4 · DSP

Sampler voice DSP plus richer effects

Add full envelopes, filters, LFOs, dynamics, utility, better time/space effects, parallel paths, sends, quality modes, and modulation-ready parameters.

5 · Advanced playback

Behavior beyond static zone selection

Weighted and conditional alternation, voice limits, note stealing policies, legato/mono/glide, humanization, microtuning, multi-output routing, and more expressive MIDI.

6 · Stable extensibility

Versioned APIs before scripts

Stabilize object identities, event semantics, parameter descriptors, budgets, package persistence, and diagnostics. Scripting should compose these capabilities, not replace them.

Repository-corpus signal. Across the checked-in and demonstration SFZ material, frequent currently weak or unmapped families include key_group/off_by/off_mode, ampeg_attack, velocity curves, note_polyphony, sw_*, key_offset, CC crossfades, group/region labels, and rt_decay. These are better roadmap inputs than chasing the entire SFZ opcode universe alphabetically.
DSP direction

Keep the pipeline. Upgrade the vocabulary.

The existing architecture already does the hard operational work: validate and build off the audio thread, compile immutable graphs, bound memory/cost, smooth parameters, and activate generations safely. The roadmap should preserve that foundation while making DSP more musical, composable, and consistent to author.

Keep

Prepared, versioned, real-time-safe graphs

Immutable graph plans, stable slot IDs, scoped processing, parameter descriptors, control-law mapping, explicit state/tail cost, deterministic validation, and last-known-good activation.

+
Add

A coherent DSP authoring contract

Reusable voice blocks, a unified modulation interface, standard units and response laws, presets/defaults, latency and quality metadata, modulation rates, parallel routing, sends, and richer algorithms.

Tier A · Essential

Sampler voice shaping

  • Full delay/attack/hold/decay/sustain/release envelopes.
  • Stable multimode filter with key/velocity tracking and filter envelope.
  • Tempo/free LFOs with retrigger, phase, fade, and standard shapes.
  • Pitch bend, glide, tuning tables, start/loop-position modulation.
Tier B · Practical

Mixing and routing

  • High-pass/low-pass utility, stereo width, polarity, mid/side, channel tools.
  • Compressor, limiter, gate, transient shaper, and envelope follower.
  • Aux sends, returns, parallel wet/dry paths, and explicit tail/latency behavior.
  • Reusable chains and versioned DSP presets in native projects/packages.
Tier C · Character

Space and tone

  • Improved saturation with selectable topology and bounded oversampling.
  • Phaser, flanger, ensemble, rotary, and deeper chorus variants.
  • Better tempo-aware delay and algorithmic reverb.
  • Convolution with streamed IR preparation and deterministic package inclusion.
DSP design rule: every parameter declares its unit, domain, default, smoothing, modulation rate, automation safety, state/tail/latency cost, and serialization version. If it cannot satisfy the callback budgets, it does not enter the performance graph.
Outcome roadmap

From V1 to scripting.

This is deliberately sequenced by dependency, not calendar. Each stage should ship when its exit gate is true; stages can overlap internally, but later public promises depend on the earlier contracts.

Stage 0
V1 · Release baseline

Freeze and explain the sampler that exists.

Ship the current native sampler, bounded SFZ conversion, project/package workflow, streaming engine, performance rules, controls, and curated DSP foundation.

Publish the V1 SFZ profile

Opcode/value/scope matrix, approximation rules, unsupported semantics, and tested libraries.

Close or document package exclusions

Decide whether pan and performance-bank rejection are V1 exclusions or release fixes.

Freeze compatibility contracts

Readable project/package versions, migration policy, DSP algorithm versions, and recovery guarantees.

Release qualification

Focused SFZ, performance, DSP, streaming, host-recall, package, and installer gates.

Exit gate: a creator can predict before import which SFZ behaviors will be native, approximate, or report-only, and a published instrument preserves every feature V1 claims.
Stage 1
V1.x · Compatibility first

Break the “new instrument, new blocker” cycle.

Promote the highest-impact SFZ families into reusable native systems. Prioritize semantic blockers found repeatedly in real libraries rather than isolated parser additions.

Choke and voice policy

group, off_by, off_mode, off_time, key groups, note/group polyphony, and deterministic stealing.

Complete amplitude baseline

Delay/attack plus velocity curves, key scaling, release-time decay, and correct inherited scope.

Switch and metadata families

SFZ switch ranges/defaults/labels and stable imported names for groups, regions, and controllers.

Selection and modulation fidelity

CC crossfades, key/transpose offsets, richer random/sequence rules, and explicit unsupported-shape handling.

Reference-render harness

Event-timeline renders, aligned audio comparisons, envelope/onset/loop metrics, and listening gates.

Corpus scoreboard

Per-library sound-critical blockers, import disposition counts, and regression ownership.

Exit gate: representative piano, drum, orchestral, keys, and texture libraries import without manual repair for the declared profile, with measured audio-fidelity evidence.
Stage 2
V1.x · Articulation system

Make articulations a performance language.

Expand first-class articulation objects beyond a single latch key. This is where SFZ keyswitch import and native articulation authoring converge.

Activation modes

Latch, momentary, toggle, CC range, program change, and host-selectable activation with explicit consumption.

Composite eligibility

Key/velocity/CC/pedal/channel conditions, legato state, previous note, and deterministic precedence.

Transitions and fallback

Default/fallback articulation, attack→release pairing, transition samples, mutual exclusion, and reset behavior.

Articulation-owned behavior

Routing, controls, macro defaults, tuning, voice policy, and DSP overrides without copying zones.

Interchange projection

Map supported sw_* semantics into native rules and report ambiguous switching topologies precisely.

Compiler budgets

Flatten rule graphs into bounded, string-free tables while retaining stable authoring IDs and diagnostics.

Exit gate: a multi-articulation library can be authored, imported, published, recalled, and switched without custom code or duplicated mapping.
Stage 3
V1.5 · Modulation & DSP

Turn the sampler into a sound-design instrument.

Land the common modulation contract first, then use it to drive both voice DSP and insert/bus DSP. This avoids another collection of one-off CC implementations.

Unified modulation graph

Velocity, key, CC, pitch bend, channel/poly pressure, envelopes, LFOs, random, macros, and transport sources.

Voice DSP

Full envelopes, multimode filters, filter/pitch envelopes, LFO, glide, sample-position and loop modulation.

Richer effect suite

Dynamics, utility, deeper modulation effects, improved delay/reverb/saturation, and convolution.

Practical routing

Aux sends/returns, parallel chains, dry/wet topology, reusable chains, and deterministic package ownership.

Quality and cost modes

Oversampling, interpolation, tail, latency, state, and CPU/memory budgets as explicit prepared-graph metadata.

Musical parameter contract

Standard units, ranges, response laws, modulation polarity/depth, smoothing, defaults, and presets.

Exit gate: common subtractive and sample-shaping instruments can be built entirely with native blocks, every DSP parameter is controllable through one modulation model, and performance remains bounded.
Stage 4
V2 · Advanced sampler

Cover the hard instruments scripts usually patch.

Before introducing code, finish the declarative engine behaviors that should remain portable, inspectable, testable, and optimizable.

Advanced voice behavior

Mono/legato modes, glide, retrigger policy, voice limits, priority/stealing, release and choke refinements.

Variation engines

Weighted random, shuffle/no-repeat, conditional sequence, deterministic seeds, timing/gain/tune humanization.

Expression and tuning

Pitch bend, pressure, per-channel routing, MPE/per-note expression, Scala/KBM and per-note tuning.

Large library topology

Mic positions, multi-output buses, purge/preload policy, background source conversion, and package parity.

Event and transport depth

Tempo-sync, beat/transport conditions, program state, release velocity, held duration, and previous-note context.

Declarative action graph

Versioned conditions/actions that compile into the same bounded event tables a future script runtime will target.

Exit gate: the engine covers recurring sampler behavior declaratively, and the remaining extension requests are genuinely custom logic rather than missing core features.
Stage 5
V2.x · Scripting

Add scripting as a safe extension layer.

Scripting arrives last because it depends on stable objects, events, DSP parameters, articulation rules, persistence, and budgets. It should extend the engine while preserving deterministic publication and real-time guarantees.

Two execution domains

Off-thread authoring/build scripts for project transformation; bounded performance scripts for event decisions.

Versioned capability API

Stable zone/group/layer/articulation/control/DSP handles, event records, parameter descriptors, and feature discovery.

Compile, do not interpret, on audio

Validate scripts off-thread and compile performance behavior to bounded bytecode or declarative actions.

Hard sandbox

No file/network/UI access from performance code; fixed instruction, memory, fan-out, recursion, and callback-time budgets.

Determinism and recovery

Seeded randomness, serializable state, migration/version rules, diagnostics, timeout/fault isolation, and last-known-good fallback.

Package trust policy

Signed capability declarations, explicit user trust, content provenance, and safe behavior when scripts are unavailable.

Exit gate: custom behaviors can ship in a package without allocation, I/O, unbounded work, nondeterministic recall, or the ability to destabilize the audio callback.
Priority and sequencing

What should happen first.

The practical order is driven by customer pain and architectural leverage. SFZ and DSP should begin together after the V1 freeze, with the articulation and modulation contracts acting as their shared foundations.

Do not use “full SFZ support” as the milestone. SFZ has dialects, vendor extensions, and ambiguous behavior. The durable goal is an explicit, growing profile with reference-corpus evidence and zero silent loss of sound-critical semantics.
