Outcome and boundaries

Creator outcome

An author creates named articulations, bulk-assigns zones, learns C0/D0 key switches, and declares release, pedal, one-shot, choke, and Round Robin reset behavior without editing JSON.

Player outcome

A published instrument responds predictably to performance MIDI: switches are silent, pedal transitions are sample accurate, releases sound at the correct physical or effective event, and repeated performance is deterministic.

Engine outcome

The project compiles author-friendly IDs and rules into immutable indices and bounded lookup tables. Mutable performance state remains lane-local and activation-safe.

Program boundary: this is a declarative event router, not a general scripting language or modulation engine. Version 1 supports a fixed vocabulary of events, conditions, and actions with explicit limits and validation.
Compiled-instrument boundary: the future compiled/playable instrument is content only. It contains prepared samples, mappings, performance rules, presets, artwork, and metadata, but it does not contain or install a runtime and it is not a VST. The installed DRS VST3 or standalone player supplies the runtime engine and opens the compiled instrument package.
Trigger-key policy: consuming trigger keys is mandatory, not optional cleanup. A key switch and its matching note-off are intercepted before playable routing, so reserved C0/D0 inputs cannot accidentally start sample voices.
Important semantic split: note-off means the performer physically released a key. release means the sounding note actually enters release after sustain deferral. Key-up mechanical noises may use note-off; damper-contact samples should normally use release.

Architecture decisions

Keep fast note routing

Ordinary playable note-on routing remains a precompiled zone scan/table path. The rule layer changes state or emits bounded actions; it does not interpret a general expression tree for every zone and event.

Compile author vocabulary

Authoring uses stable string IDs. Publication resolves them into numeric articulation, trigger-route, choke-group, and RR-pool indices. Unknown or ambiguous references block Publish.

State belongs to the playback lane

Selected articulation, held-note contexts, consumed-switch notes, pedal state, and RR cursors live in each SamplerPlaybackContext/voice pool. Preview and Performance never share mutable state.

Activation is explicit

Successful Publish installs a new immutable program at a block boundary. State migrates only by stable ID under a written policy; failed publication preserves the last-known-good generation.

Do not make performanceBanks.triggerSlots the core articulation model. Those slots mix phrase-launch concepts with articulation targeting and currently lack executable input identity. First-class articulation activation belongs in the instrument performance program; phrase banks may reference it but must not own it.

Event semantics and deterministic order

Semantic eventProduced whenContextTypical action
note-onMIDI note-on with velocity > 0Channel, note, attack velocity, sample offsetSelect articulation for a consumed key switch or start playable zones.
note-offMIDI note-off or note-on velocity 0Channel, note, release velocity, retained attack velocity/articulationPlay immediate key-up/mechanical samples and mark the physical key released.
releaseA held voice is allowed to enter releaseOriginal note, attack/release velocity, attack articulation, pedal causePlay damper/release samples. Deferred until pedal-up when sustain owns the note.
pedal-downCC64 crosses from <64 to ≥64Channel/omni policy, CC value, sample offsetSet sustain state, trigger pedal-down noise, optionally reset RR pools.
pedal-upCC64 crosses from ≥64 to <64CC value, sample offset, deferred-note setClear sustain state, release deferred notes, trigger release routes and pedal-up noise.

Same-sample action precedence

  1. Apply panic/reset and activation-boundary policy.
  2. Normalize the raw MIDI event and detect state transitions.
  3. Evaluate consume/select-articulation actions.
  4. Apply authored RR reset actions.
  5. Apply choke actions to existing voices.
  6. Release/defer existing note voices and emit effective release events.
  7. Resolve and start trigger routes using the final state for that sample offset.
A consumed key-switch note-on and its matching note-off never reach playable zone routing. The engine keeps a bounded consumed-note bitset so the release half is also suppressed.

Proposed authored model

The exact C++ names may change during Sprint 0, but the persisted concepts and ownership should remain stable. Project schema moves from 5/4 to 6/5; compiled instrument schema moves from 2 to 3.

First-class articulation

  • Stable id, editable displayName, authored order, and exactly one default.
  • Optional latch-style key-switch activation with numeric MIDI note.
  • Zones reference an existing articulation ID.
  • Deletion requires reassignment or an explicit cascade decision.

Zone event declaration

  • Trigger event: note-on, note-off, release, pedal-down, or pedal-up.
  • Sustain condition: any, pedal-up, or pedal-down.
  • Pitch source: follow event note or fixed root key.
  • Playback mode: gated or one-shot.
  • Optional choke membership/targets and RR reset policy.

Compiled runtime design

Host MIDIJUCE supplies bounded MIDI events with sample offsets.
NormalizeConvert note, CC64, panic, and reset messages to semantic events.
StateUpdate held notes, consumed switches, articulation, and pedal state.
MatchRead dense event-indexed compiled rule ranges; no string scans.
ActionsSelect, consume, reset RR, choke, release, or request trigger routes.
RouteResolve articulation, key/velocity, RR, crossfade, and pedal conditions.
VoicesStart or release existing fixed-capacity sampler voices.

Immutable program

SamplerRenderModel owns compiled articulation descriptors, event-index ranges, trigger routes, choke masks, and RR reset actions retained by the activation payload.

Mutable state

The playback context owns selected articulation index, pedal state, 128-note held/consumed records, RR cursors, and bounded diagnostic counters.

Generation safety

Held voices retain their originating model. Note contexts retain the attack generation so release/choke behavior never dereferences a retired program.

The compiler rejects behavior it cannot flatten safely. Publication must never fall back to interpreting author JSON or silently dropping a condition.

  • PE-001 Freeze same-offset ordering, especially pedal-up → deferred release → release sample → pedal-up noise.

  • PE-003 Freeze migration policy for implicit articulations and existing performanceBanks.triggerSlots.

  • Every requested behavior has one unambiguous event/condition/action definition.

  • No design question is deferred to the audio callback implementation.

Primary seams: new contract doc, new fixture JSON/MIDI timelines, tests/CMakeLists.txt, focused red-test sources.

Risks, mitigations and non-goals

Primary risks

  • Rule-engine creep: expressions, arbitrary CC math, and scripting would destabilize the realtime contract. Keep the v1 vocabulary closed.
  • Voice/event explosion: pedal-up can fan out across many notes. Budget actions and reject over-capacity programs before audio.
  • Generation ownership: release events may occur long after attack. Retain generation-safe note context and model ownership.
  • Migration ambiguity: an articulation named “sustain” is not pedal state. Never infer pedal behavior from names.
  • Switch collisions: store numeric notes, visualize reserved keys, and apply one explicit validation policy.
  • Release recursion: event-triggered voices do not recursively emit authored release events in v1.

Explicit non-goals

  • Half-pedal, repedaling depth, sympathetic resonance, or physical piano modeling
  • Momentary or velocity-selected articulation switching
  • General CC ranges beyond the dedicated CC64 sustain state
  • Aftertouch, MPE/per-channel articulation, legato transition detection, or tempo rules
  • Modulation matrix, envelopes/LFOs, filters, scripting, or a general expression VM
  • Phrase-engine redesign or making performance-bank phrase slots part of core routing
  • Compiled/encrypted distribution packaging; that is the next vertical milestone after this engine contract stabilizes

Program definition of done

  1. Articulations are first-class project entities with stable identity, exactly one default, safe transactions, migration, and full UI management.
  2. C0/D0 latch key switches select articulations at sample offsets and are consumed on both note-on and note-off.
  3. Zones can respond to note-on, physical note-off, effective release, pedal-down, and pedal-up with any/up/down sustain conditions.
  4. Release and pedal samples support follow-note/fixed-root pitch and reliable one-shot playback.
  5. Exclusive/choke relations and RR reset rules compile to bounded numeric runtime data and behave deterministically.
  6. Legacy projects migrate without playback regression; legacy compiled instruments continue to load.
  7. Publish, Preview, Performance, preset recall, host-state recall, and activation retirement obey one documented state policy.
  8. Authors can build the Piano Lite and two-articulation strings fixtures entirely in the shared UI.
  9. Debug/Release automation, offline renders, realtime soak, accessibility tests, and REAPER validation are green.

North-star acceptance statement

An author opens Practical Sampler, creates Sustain and Staccato, assigns C0 and D0, maps main/release/pedal samples, sets choke and RR reset behavior, publishes, and plays the result in REAPER with no hand-edited JSON and no audible trigger keys.

Next milestone: compile that proven behavior into the first self-contained distributable instrument package.
